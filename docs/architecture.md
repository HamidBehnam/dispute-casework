# Architecture notes

The current state of the parts that exist. Decisions and measured results are in `docs/adr/`.

## Corpus

`corpus/ecfr/<snapshot>/` holds one dated snapshot of a regulation part from the eCFR: the part as XML from the versioner API and as HTML from the renderer endpoint, both as downloaded, `chunks.jsonl`, `embeddings.npy` and `manifest.json`. The manifest records the snapshot date, both source URLs as fetched, the latest amendment date, the reason for the pin and the date it was checked, the sha256 of the other four files, the chunk counts, the embedding model and the parser and content-format versions. The eCFR is an unofficial edition of the CFR, and the manifest labels the snapshot as such. Regulation E is pinned to the text of 2023-04-19; ADR 0004 gives the reason and the rule for moving the pin.

`ecfr.parse_part` yields the paragraphs of the part, each with its ID. For regulation text the ID is the eCFR's own: the id of the paragraph's node in the rendered HTML without its `p-` prefix, such as `1005.11(c)(2)(i)`, and a paragraph that sits directly in a section takes the section's id. A node that holds only a designator and a heading is not a paragraph of its own; its heading joins the heading path of the paragraphs below it. The eCFR gives the comments of Supplement I no ids of their own, so their IDs, such as `1005.11(c)-3`, are rebuilt from the order of the comment numbers in the flat XML. Regulation text is tagged `binding` and Supplement I `official_interpretation`. Each paragraph is one chunk. Its content is the paragraph ID, the heading path and the paragraph text on three lines; that one string is embedded, keyword-indexed and reranked.

`python -m dispute_casework.corpus_build` has one command per step: `fetch` downloads the two source files, `embed` writes the chunk and embedding files from one embed call, and `load` rebuilds the `chunks` table. `load` checks every file against the manifest before it touches the database.

## Retrieval

`retrieval.py` holds three plain functions. `embed` calls the embedding deployment. `retrieve(store, embedding, keywords)` runs the vendor's hybrid search on Postgres (pgvector cosine distance and a stored `tsvector` column, fused by reciprocal rank fusion) and returns twenty candidates. `rerank` sends candidates to the rerank deployment and returns them in relevance order. Every search builds its own `HybridSearchConfig`; `INVARIANTS.md` names the tests that hold this in place. `retrieve` takes the query embedding for the dense leg and a short keyword string for the keyword leg, and raises `ValueError` when the keyword string is empty or blank, because the vendor then returns the dense leg without fusion.

Model clients are built in `foundry.py` with an explicit 60-second timeout. Rate limits are handled by the retries of the OpenAI and cohere SDKs; this repository's code batches nothing by token count and waits nowhere.

The database is the single service in `compose.yaml`. Nothing is created when the container starts: the extension and the table are created by `corpus_build load`, and by a session fixture in the tests.

## Exit test

`tests/test_exit.py` replays one recorded run of the five retrieval arms over the 30 queries in `tests/queries.json`. Recall@k of a query is computed by ir-measures inside a DeepEval metric, and the figure for a set of queries is the mean over its queries. The gates on the keyword leg and on recall@20 are asserted. The gate on recall@5 after rerank is not met in the recorded run, 0.84 against a threshold of 0.85 and 0.88 before rerank (ADR 0004); its test is an expected failure that fails the suite once the gate is met.

`docs/results/0004-exit-run.json` holds every published figure of the run: the mean and the pooled count per stratum and arm, the Wilson intervals and the rerank comparison from scipy, and the rank of every expected ID per query. It is generated by code from the replayed run; a test regenerates it, and when the committed file differs the test fails and names the regenerated file.

DeepEval is used as a library only. `tests/conftest.py` sets `DEEPEVAL_TELEMETRY_OPT_OUT`, `DEEPEVAL_DISABLE_DOTENV`, `DEEPEVAL_FILE_SYSTEM=READ_ONLY` and `DEEPEVAL_DISABLE_LEGACY_KEYFILE` and removes `CONFIDENT_API_KEY` before anything imports it, so it sends no telemetry, reads no `.env` or key file and writes nothing. pytest runs with DeepEval's plugin and the four plugins it installs turned off, `.deepeval/` is ignored by git, and CI sets the telemetry opt-out for the whole workflow.

## Recorded model responses

Tests that reach a model replay recorded responses (pytest-recording on vcrpy). The default record mode is `none` and pytest runs with `--block-network`, so a test run makes no model call. A cassette stores the sha256 of each request body in place of the body, so it carries no query or regulation text. Authorization headers and the request headers that describe the recording machine are removed. Response headers are stored as received: a probe of 200 and 429 responses from both deployments found request IDs, model, deployment and region names and rate-limit counters in them, and no account, subscription or tenant identifier and no cookie. A rate-limit response is never stored: a call that the SDK retried is recorded as the response that succeeded. A change to a query, a chunk, a retrieval parameter, a model deployment or the request shape of an SDK changes the hash, and the affected test fails until its cassette is recorded again.

Recording a cassette again needs `FOUNDRY_ENDPOINT`, an Azure CLI login with access to the Foundry account and the database from `compose.yaml` running, and is run as `uv run pytest --record-mode=rewrite tests/test_retrieve.py tests/test_exit.py`. The exit test makes 60 rerank calls against a limit of 20 requests a minute; the cohere SDK's retries wait the limit out, and the recording takes about three minutes.

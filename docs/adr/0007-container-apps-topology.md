# ADR 0007: Container Apps topology behind Cloudflare

Status: Accepted.

## Context

The service runs four processes inside one trust boundary: the backend, the FastMCP server, the Cerbos policy engine and the mock bank. In production it needs public TLS on its own hostname, an origin that only the edge can reach from the internet, identities and secrets with no stored credential, a streamed response that stays open for minutes, and close to no cost between demos. The root `infra/app` provisions the topology. Measured figures are in `docs/results/0007-topology.json`, generated by `dispute_casework.topology_results` from the raw readings under `docs/results/0007-topology-raw/`; this record names their keys.

## Decision

- **One Container App with four containers** in a workload-profiles environment that declares only the Consumption profile, in single revision mode with at most one replica. The containers are the backend, Cerbos 0.55.0 pinned by digest with strict evaluation and schema rejection over an empty policies directory, and two containers for the FastMCP server and the mock bank, which run the backend image on their own ports until those services are built. Every probe's timing is set explicitly; the three application containers are probed over TCP and Cerbos on its own health path, so no probe carries the origin header.
- **Cloudflare in front**: a proxied A record to the environment's static IP, SSL mode Full (strict), and a Cloudflare Origin CA certificate bound to the custom domain by SNI. The certificate's key is generated in Key Vault and is exportable: the environment imports the certificate through the vault's secret, and the secret's value holds the private key only when the policy marks the key exportable. The signing request is committed as `infra/app/origin.csr`. The Key Vault certificate, the Cloudflare certificate, the environment certificate and the domain binding carry `prevent_destroy`.
- **The origin lock** is two checks for a request from the internet. The ingress allows only Cloudflare's published IPv4 ranges, read from the Cloudflare provider; the root refuses to plan when that list is empty, since an ingress with no rule allows every address. The application then compares `X-Origin-Secret` with `ORIGIN_HEADER_SECRET` in constant time on every route and answers 403 otherwise; it serves no OpenAPI or docs route and does not start on a secret shorter than 32 characters. A Cloudflare transform rule sets the header on every request to the hostname. The allow-list does not tell this zone apart from other Cloudflare traffic, so the header is what ties a request to this zone; a request from inside the environment by the app's name is not subject to the allow-list and meets the header check only. A developer address enters the allow-list only through `TF_VAR_developer_ip_addresses` for a direct measurement and leaves with the next apply made without it.
- **The origin header secret** is held in Key Vault, written as a write-only value, and in the Cloudflare rule, which holds it as a plain value, so it is also in the root's Terraform state and in any saved plan. The app reads it through a versionless Key Vault reference. Rotation is a new value with `value_wo_version` raised; the same apply updates the rule, and the app picks the new version up within up to 30 minutes.
- **Zone-wide settings**: the SSL mode and the rate rule (a client that sends more than 100 requests in 10 seconds is blocked) apply to the whole zone; the header rule applies to the hostname only.
- **Two user-assigned identities.** The platform identity pulls the image (`AcrPull`), resolves the Key Vault references (Key Vault Secrets User) and imports the environment certificate; it carries lifecycle `None` on the app and the job, so code never obtains its token. The main identity carries lifecycle `Main`; the backend container's environment selects it through `AZURE_TOKEN_CREDENTIALS=managedidentitycredential` and `AZURE_CLIENT_ID`. The lifecycles are set through azapi, since azurerm 5.11.0 has no argument for them.
- **Key Vault** is standard, under RBAC authorization.
- **The image** is built from one Dockerfile and pulled from the private Azure Container Registry (Basic) that the bootstrap root creates. The root references the backend image by digest (`image_digest`). The revision running now was applied before that change and runs the image built on Oct 28 from commit `973438e`, referenced by tag; rebuilding the image from the final commit and applying it by digest is assigned to the deploy step.
- **Scale to zero with the warm-replica policy.** `min_replicas` defaults to 0. One warm replica runs from the step 18 deploy while the demo is being shown, then the app returns to zero; `min_replicas` is one variable, applied in minutes. The subscription budget in `infra/foundry` (25 USD a month) is increased when the replica goes warm.
- **The stream** carries assistant-stream's heartbeat every 15 seconds. A Container Apps job with a manual trigger runs the stream measurement client inside the environment.
- **The cross-process pool budget**, which ADR 0005 assigned to this step, is not built here: no process of this step connects to the database. It moves to the step that first runs a second process against the database.

## What it does

The topology gives the four processes one replica, one network namespace and one lifecycle, with the platform's own HTTP ingress, TLS binding, Key Vault references, identity-based image pull and scale to zero, so the root holds configuration and no process of its own. Cloudflare terminates public TLS and applies the rate rule at the edge. From the internet the origin answers only requests that arrive from Cloudflare's ranges and carry the zone's header; from inside the environment the header alone decides. Code in the backend that asks for a token gets the main identity's, with no stored credential.

## What it changed and what it costs

The service now has a public hostname with Full (strict) TLS to the origin, and a direct request to the app's own hostname from outside the allow-list is refused (`claims.custom_domain_binding`, `ingress_inside`). Through the ingress and inside the environment every heartbeat stream lasted its five minutes (`gates.ingress`, `gates.internal`); through Cloudflare the first series lost two of five to a reset with the heartbeat running (`gates.cloudflare`, `stream`) and the paired series lost none (`gates_paired.cloudflare`). Both proxies cut a silent response (`claims.ingress_timeout`, `claims.cloudflare_timeout`), so the heartbeat is a requirement of the path. At zero replicas the Container Apps meters bill nothing and the resource group's floor, as billed under the free offers, is the registry and the vault (`zero_replica_floor`); no environment management meter is billed (`claims.environment_meter`). One warm replica at the current allocation costs `warm_replica_usd_per_month.usd_per_month["0.75/1.5"]`. Scale to zero costs a cold start on the first request (`cold_start_probes_summary`; the series before the explicit probe timing is `cold_start_summary`). The lock costs a secret that also lives in Terraform state and saved plans; a rotation that refuses requests until the app picks up the new version, up to 30 minutes after the apply; a certificate key that can be exported from the vault; an SSL mode and rate rule that any other hostname in the zone shares; and an allow-list that admits all of Cloudflare's traffic, whose drift against Cloudflare's published ranges is assigned to the deploy step and checked by nothing in this root yet.

## Why it over the alternatives

AKS keeps nodes running whatever the traffic, since a production cluster with a single system node pool must contain at least two nodes, while a Container App at zero replicas bills no usage. App Service with sidecars charges each VM instance of its plan, so the four containers would carry the plan's cost between demos. Azure Front Door carries a monthly base fee and Application Gateway WAF v2 a fixed hourly charge (Azure Retail Prices API), both billed while the app has no replica, where the Cloudflare features this root uses (proxying, the Origin CA certificate, a transform rule and a rate rule on the path, counted by IP) are available on Cloudflare's Free plan. Without an edge there is no fixed set of addresses for the ingress to allow, so the one public replica would take every request directly with no rate rule in front of it. Cloudflare Tunnel needs a running `cloudflared` connector to carry requests; inside the replica it stops when the app scales to zero, so no request could wake it, and outside it would be one more process that never scales to zero. Authenticated Origin Pulls needs the origin to check Cloudflare's client certificate, but the Container Apps ingress accepts any certificate issued by a trusted authority or self-signed and passes it to the app in `X-Forwarded-Client-Cert`, so the check would be code in the application, where the header compare is one standard-library call. The platform's free managed certificate needs the app to be reachable from DigiCert's addresses and a CNAME that maps directly to the app, and the vendor names Cloudflare as an intermediate that blocks issuance and renewal; the allow-list and the proxied record rule both out. A NAT Gateway gives outbound traffic a fixed address inside a virtual network, and this environment has no virtual network and no destination that admits the app by its outbound address. ACR Standard adds included storage and image throughput and Premium adds geo-replication, private endpoints and concurrency, none of which one image pulled by one app uses. A private image in GitHub Container Registry or Docker Hub would be pulled with a user name and a password secret, where the private Azure Container Registry is pulled by the platform identity with no stored credential; Docker Hub also limits downloads, and containers fail to start when the limit is reached. A public image, pulled with no credential the way the Cerbos image is, was not chosen for the backend.

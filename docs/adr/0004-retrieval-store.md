# ADR 0004: Retrieval store

Status: Proposed

## Context

The agent retrieves the governing paragraphs of Regulation E before it drafts findings, and every citation it makes is a paragraph ID that must have been retrieved. The design puts hybrid retrieval in the same Postgres that holds the rest of the application data, through the pinned LangChain Postgres package, with a reranker as a second stage and Qdrant as the recorded fallback store. Before anything is built on that choice, a spike had to answer on the real regulation text: can the eCFR text be turned into stable paragraph IDs; does hybrid search in langchain-postgres 0.0.18 work when configured explicitly, given its open defect with shared configuration; what does each stage contribute on a hand-written query set; and can the whole path be tested without network access.

Two rules bound the answer. Every AI capability is a vendor or framework component, and code is written here only where no component does the whole job, with one exception, named under "Code written here", where each such unit is listed. And the paragraph IDs of regulation text are the eCFR's own identifiers, not IDs derived here.

The following were fixed before the run recorded here.

- **Query set.** 30 hand-written queries in three strata: bare citations, exact-term queries and paraphrased questions, each with its expected paragraph IDs and a keyword string of three to five terms (the ID itself for a citation).
- **Arms.** Dense search; hybrid search with the question as the keyword query; hybrid search with the keyword string; dense search with rerank; hybrid search with the keyword string and rerank. Rerank takes the arm's twenty candidates and returns five.
- **Recall.** Recall@k of a query is the share of its expected paragraph IDs among the first k results, computed per query by ir-measures 0.4.3 as `R@k` (trec_eval's `recall_k` through pytrec-eval-terrier 0.5.10). The figure for a set of queries is the mean of the per-query values, each query counting the same, taken with the standard library's `fmean`. The pooled count, expected IDs found over expected IDs (`NumRelRet` over `NumRel` on the run cut to k), is reported beside it and is not gated.
- **Gates.** They apply to the exact-term and paraphrased strata (the gate strata). The citation stratum is measured and reported, never gated, because an exact citation is served by the citation lookup in the design.
  - a. Two consecutive searches each use their own keyword query.
  - b. With keyword strings, the keyword leg returns rows for at least 90% of gate-strata queries (23 of 25).
  - c. Recall@20 of hybrid search with keyword strings is at least 0.90.
  - d. Recall@5 of hybrid search with keyword strings after rerank is at least 0.85 and not below recall@5 of the same arm's fused top 5.
  - e. One live double run of the hybrid and rerank arm returns the same top 5; reported, not gated.

  The 25 gate-strata queries include one with two expected IDs, so the mean moves in steps of 0.02: gate c is met from 0.90 and gate d from 0.86.

  The gates were first stated on the pooled count. The definition was changed to the mean per query, with the thresholds unchanged, after an earlier run under the pooled definition had been measured and before the run recorded here; on that earlier run both definitions give the same verdict on every gate.
- **Fault attribution.** A failed check counts against the store only if the dense leg alone shows the paragraph to be retrievable. Parser, chunking and label faults are fixed in code and do not count against the store.
- **Levers.** `rrf_k`, and the text-search language constant with a table rebuild. A custom fusion function, hand-written keyword SQL and merging in Python are excluded.
- **Flip trigger.** The store moves to Qdrant only if hybrid search with keyword strings has a lower recall@20 than dense search on the exact-term stratum and a bounded sparse-hybrid run on Qdrant beats it on the same queries.
- **Keyword leg.** If dense search with rerank meets the targets on every stratum, the keyword leg is recorded as optional.
- **Statistics.** Every figure is generated by code from the replayed run into `docs/results/0004-exit-run.json`, and a test fails when that file is not what the recorded run produces. Statistics come from scipy only. The interval for a cell is `scipy.stats.binomtest(queries whose recall@k is 1.0, queries in the cell).proportion_ci(method="wilson")` at the 95% level, labelled as the share of queries with every expected ID found. The reranked top 5 is compared with the fused top 5 by query: the number of queries where rerank is higher and where it is lower, and `scipy.stats.binomtest(higher, higher + lower, 0.5)` when at least one query differs. There is no bootstrap and no interval on a pooled count. A non-significant test is not evidence that rerank is no worse.
- **Live sessions.** The vectors and the recorded responses come from two sessions on the Foundry account, under the Azure CLI login, with the deployments as they are: no capacity or deployment change is made for them, and no wait is added in this repository's code. Session logs stay outside the repository.
  - *Embedding session* (deployment limits: 10,000 tokens a minute and 10 requests per 10 seconds). Response headers are captured with an httpx response hook on a client passed to the same model class, or through the SDK's raw-response access if the hook does not fire. Probes first: one smoke call; one request of 16 chunks; then the first 96 chunks as six requests back to back, recording for the first 429 its headers, its error code, the SDK's retry line and whether the retry returned 200; then a 90-second wait. Stage 1 is the client as configured, on the SDK's default retries, in one embed call over all 1,742 contents. It passes if it completes without an exception, every request ends in a 200, every 429 is followed by a 200 for the same request, `embeddings.npy` is (1742, 1536) float32 and the manifest verifies. Stage 2 runs only if stage 1 fails: the same call with `max_retries` set to the larger of 6 and 75 divided by w, rounded up and capped at 40, where w is the number of seconds the SDK waited before its first retry in stage 1; it is skipped if stage 1 shows the SDK declining to retry because the server's retry-after exceeds its maximum. The files of the stage that passes become the committed snapshot, and the token-count batching and the pacing written here are deleted; `max_retries` appears in the code only if stage 2 is the stage that passed. If neither passes, the run stops there. The new vectors are checked against the previous ones on the chunks whose content is byte-identical in both snapshots: `numpy.testing.assert_allclose(new, old, rtol=0, atol=0.01)`.
  - *Rerank session* (deployment limits: 20,000 tokens a minute and 20 requests a minute). One 20-candidate call through the SDK's raw-response access records the response header names, any rate-limit values and the billed search units. After at least 90 seconds without a call, one fixed request (the twenty hybrid candidates of the first paraphrased query) is sent with `max_tokens_per_doc=512`, back to back with retries off, until the first 429 or 25 calls; after another 90 idle seconds the same request is sent without `max_tokens_per_doc`. The cap is removed unless the uncapped request is rejected or its series reaches the first 429 two or more calls earlier than the capped series. If the 429 carries a header the cohere SDK waits on (an integer or HTTP-date `retry-after`, or `x-ratelimit-reset`), the recording runs on the SDK's default retries; otherwise the SDK's own retry count on the client is raised to 7. The three cassettes are then recorded once; the recording passes if the tests pass with gate d as measured and the cassettes hold only 200s. The hybrid and rerank arm is then run live a second time for gate e and its top 5 and twenty candidates are compared per query with the recorded run; that comparison is an observation, not a recording.

## Decision

- **Store.** PostgreSQL with pgvector through langchain-postgres 0.0.18 stays. The flip trigger did not fire: on the exact-term stratum hybrid search with keyword strings and dense search both have recall@20 of 1.00 (9/9), so no Qdrant run was made. What this query set can and cannot show: dense search already reaches every expected ID at 20 on the exact-term stratum, so this set could show hybrid search doing worse there, which it did not, but not doing better, and the store stays by the rule fixed before the run, not on evidence that hybrid search raises recall@20 on the gate strata, where both arms have 0.96 (25/26). langchain-postgres 0.0.19 was released on 2026-10-06; the pin stays at 0.0.18 for this record, and the upgrade is a separate change.
- **Gate d.** Recorded as not met, as measured: on the gate strata recall@5 after rerank is 0.84, under the threshold of 0.85 and under the 0.88 of the fused top 5. The thresholds, the chunking, the labels and the recorded run are left as they are. The exit test carries gate d as an expected failure that fails the suite once the gate is met.
- **Corpus pin.** Regulation E is pinned to the eCFR text of 2023-04-19, the date of the last Part 1005 amendment in force. Later eCFR versions carry the amendments of 89 FR 106768, which Public Law 119-10 (May 9, 2025) disapproved before they took effect. `corpus/ecfr/2023-04-19/` holds the part as the versioner's XML and as the renderer's HTML, both as downloaded, with `chunks.jsonl`, `embeddings.npy` and a `manifest.json` that records both source URLs as fetched, the sha256 of the four other files, the latest amendment date reported by the versioner, the reason for the pin, the date it was checked and the label "unofficial eCFR snapshot". The eCFR is not an official legal edition of the CFR. Appendices A to C are not parsed; they are deferred to the corpus step, where the model forms get the legal status `model_form`.
- **Refresh rule.** List the amendment dates since the pin from the versioner, read each amending Federal Register document, and check for a Congressional Review Act disapproval. The pin moves only if every amendment it brings is in force.
- **Corpus source.** The paragraph IDs, text and hierarchy of the regulation come from the eCFR's renderer output, `https://www.ecfr.gov/api/renderer/v1/content/enhanced/<date>/title-12?part=1005`, stored with its sha256 beside the versioner XML. The renderer endpoint is outside the eCFR's published API specification; its identifiers are the anchors of the public eCFR pages. Supplement I is read from the versioner XML.
- **Paragraph IDs.** The ID of a regulation paragraph is the id of its node in the eCFR's file, verbatim, without the `p-` prefix: `1005.11(c)(2)(i)`. A paragraph directly inside a section, with no id of its own, takes the section's id (`1005.2`, `1005.30` and `1005.35`). A node that holds only a designator and a heading is not a chunk; its heading goes into the heading path of its children. A node's text excludes its descendants. A node without paragraph text raises, and so do a node with more than one paragraph of its own and an ID seen twice. The eCFR gives the comments of Supplement I no ids of their own, so they keep the IDs the comment parser assigns from the XML: `1005.11(c)-3` and `1005.11(c)(4)-5.i`, and `1005.A-1` for comments on Appendix A, a form that is provisional until the corpus step. The comment parser raises on a comment without a designator, on a designator more than one level below the paragraph before it and on a Supplement I heading of an unknown form. It places every designator of a comment by its form alone, with no check against the paragraph before, so a gap in a sequence is accepted. Three defects of the source are handled, each by its own rule: under 32(b)(1) the run of comments 2 to 7 is printed twice, and a comment whose number is not above that of the last comment kept under the same heading is dropped with its sub-paragraphs; the heading of 17(b)(3) lost its tag and sits at the end of the preceding paragraph, from where it is recovered; and comments 1 and 2 under 20(c)(4) are printed as one paragraph, which is split where a comment number follows a sentence without a space. Regulation text is `binding`, Supplement I `official_interpretation`.
- **Chunking.** One chunk per paragraph. The content is the paragraph ID, the heading path and the paragraph text on three lines (content format 1); the same string is embedded, keyword-indexed and reranked.
- **Embeddings.** text-embedding-3-large at 1536 dimensions, generated once into a float32 `.npy` file row-aligned with `chunks.jsonl`, by one embed call that sends 16 chunks a request. Requests carry raw strings (`check_embedding_ctx_length=False`). Rate limits are left to the SDK's retries at langchain-openai's own default of two, which it passes to the SDK client: no `max_retries` is set, and nothing in this repository batches by token count or waits. The files are committed to plain git; Git LFS starts with the first file over about 50 MB and is set up before that file is added.
- **Table.** Exact search, cosine distance, `PGVectorStore` on the psycopg 3 driver. Table `chunks` is created by the vendor's `init_vectorstore_table` with typed metadata columns (`paragraph_id`, `part`, `section`, `source`, `legal_status`, `snapshot`), a stored `content_tsv` column in `pg_catalog.english`, no JSON metadata column, no vector index and no GIN index at this size. Row IDs are `uuid5(snapshot:paragraph_id)`. The table is created and loaded by an explicit step, after the manifest hashes verify; nothing runs at container start.
- **Hybrid search.** Every search builds a new `HybridSearchConfig`: the stored tsvector column, reciprocal rank fusion with `rrf_k` 60, 40 rows per leg, and `k` 20 candidates passed explicitly because the vendor overwrites `fetch_top_k` with `k`. The keyword query is a separate short string, and `retrieve` raises `ValueError` when it is empty or blank. The text-search language is one constant that the vendor applies when rows are inserted (the store-level config) and when they are queried (the per-call config). `init_vectorstore_table` takes a whole `HybridSearchConfig` but reads only its `tsv_column`, which it escapes and writes back into the config, and creates a plain `TSVECTOR NOT NULL` column; the language and the other fields play no part in the table.
- **Rerank.** Cohere-rerank-v4.0-fast through the existing client, top 5. Requests carry no `max_tokens_per_doc`, and the cohere client is built with the explicit 60-second timeout and `max_retries=7`; the rerank session under Findings gives the reason for the cap and the retries.
- **Database image.** `pgvector/pgvector:0.8.2-pg17`, pinned in `compose.yaml` by the digest of its multi-platform image index (linux/amd64 and linux/arm64) and used by CI through `docker compose`. The pin follows the PostgreSQL and pgvector versions Azure Database for PostgreSQL flexible server offers, not the newest image, so it is not on the dependency update bot.
- **Recorded responses.** pytest-recording 0.13.4 on vcrpy 8.3.0, record mode `none` and the network blocked by default. A cassette stores the sha256 of each request body; authorization headers and the request headers that describe the recording machine are filtered; response headers are stored as received; a rate-limit response is dropped by a response hook, so a call the SDK retried is stored as the response that succeeded. For this step the recorded embedding response is the cache of query embeddings; an evaluation set of real size will want a plain file.
- **Evaluation tooling.** Recall@k is computed by ir-measures 0.4.3 inside a DeepEval 4.2.8 metric class that DeepEval's `evaluate()` runs; the statistics come from scipy 1.18.1. ir-measures calls trec_eval through pytrec-eval-terrier 0.5.10, which compiles trec_eval 9.0.8 sources whose file headers read "research, non-commercial purposes"; it is a test-only dependency and no part of it ships with the service. DeepEval is used as a library: it is switched off before import (no telemetry, no `.env` or key file read, read-only file system), its pytest plugin and the four plugins it installs are not loaded, and one test holds those switches in place. The recall metric is deterministic and could be computed by ir-measures alone; it runs inside DeepEval so that later evaluation steps run the same metric beside their model-judged ones, at the cost of the dependencies and the switches this record lists.
- **Next configuration.** Fixed here, before it is built, for the corpus step, in this order: the label policy for lead-in and parent/child paragraphs is settled first as a domain question (which paragraph is the correct citation); then a chunking rule that can be decided from the source files alone, under which lead-ins and list items carry their context, is applied to every chunk and every label; the corpus is embedded again as a new configuration under its own tag; it is evaluated on new queries written after the rule and before the run; and the result below is kept beside the new one.

## Findings

The exit run was recorded on 2026-10-06 against PostgreSQL 17.10 with pgvector 0.8.2, SQLAlchemy 2.1.1 and psycopg 3.3.6. Every figure of that run below is in `docs/results/0004-exit-run.json`, which a test regenerates from the recorded responses. Figures marked as an observation come from a named live session and are not reproduced by a test.

**Corpus.** The sizes and counts of this paragraph are counted from the committed snapshot files and are not in the results file. The versioner XML is 858,281 bytes (sha256 `04c370d9…8a9d7f74`) and the renderer HTML 1,401,436 bytes (sha256 `4aacbd2d…4a577d8b`); the versioner reports 2023-04-19 as the latest amendment date at the pin. The renderer file has the regulation's 27 sections with 834 paragraph nodes, each holding one paragraph of its own. 96 of them hold only a designator and a heading (four a designator alone) and are not chunks, and three sections open with a paragraph that has no id and takes the section's, which leaves 741 regulation chunks. Four chunk texts start with one designator where the XML prints two, "(a)(1)", because their parent node has no heading to pass down. Supplement I has 1,012 paragraph elements, 1,013 comment paragraphs once the two comments under 20(c)(4) are split; the second run under 32(b)(1), 12 paragraphs, is dropped, which leaves 1,001 comments and 1,742 chunks, each with a unique ID. Comments on Appendix A carry the provisional section value `1005.A`, which is why the snapshot test counts 28 distinct section values.

**Embedding session** (observations, 2026-10-06, Azure CLI login). One request of 16 chunks returned 200 with `x-ratelimit-limit-tokens: 10000`. Six requests of 16 chunks sent back to back all returned 200, so that probe met no rate limit. Stage 1 then passed: one embed call over the 1,742 contents made 109 requests, each ending in a 200, in 29.5 minutes; 50 responses were a 429 and each was followed by a 200 on the SDK's first retry, after waits of 1 to 59 seconds that add up to 28.0 minutes. Stage 2 was not run and no `max_retries` is set on the embedding client. Twelve requests sent back to back afterwards through a client with a response hook, a probe that was not among the steps fixed before the run, captured the 429: `retry-after: 56` and `x-ratelimit-reset-tokens: 56`, no `retry-after-ms`, error code `RateLimitReached`; the SDK logged "Retrying request in 56.000000 seconds (retry 1 of 2)" and the retry returned 200. On the 1,648 chunks whose content is byte-identical in the previous snapshot, the new vectors pass `assert_allclose(new, old, rtol=0, atol=0.01)`; the largest absolute difference in a component is 0.0092. `embeddings.npy` is 10.7 MB.

**Rerank session** (observations, 2026-10-06, Azure CLI login). One 20-candidate call returned 200 with `x-ratelimit-limit-requests: 20`, `x-ratelimit-limit-tokens: 20000`, both with a renewal period of 60 seconds, and was billed one search unit. The fixed request sent back to back with `max_tokens_per_doc=512` returned 22 times 200 and a 429 on call 23; sent without the cap after 90 idle seconds it again returned 22 times 200 and a 429 on call 23, with the same top 5 and one billed search unit a call. The cap is therefore removed. Both 429s carry `retry-after-ms` (302 and 381) and `x-ratelimit-reset-requests: 60`, and neither `retry-after` nor `x-ratelimit-reset`; the error code is `RateLimitReached`. cohere 7.2.0 waits on an integer or HTTP-date `retry-after` or on `x-ratelimit-reset` as an absolute time. It looks up `retry-after-ms` but never waits on it, because its parser compares the header string with a number and discards the `TypeError`, and it does not look up `x-ratelimit-reset-requests`. It backs off exponentially from one second, so the client's retry count is raised from 2 to 7. The three cassettes were then recorded once, in 2 minutes 46 seconds on those retries: 64 calls returned 200, and 55 rate-limit responses were retried by the SDK and are not stored. The exit cassette holds 62 interactions, two embedding requests and 60 rerank calls, each billed one search unit.

**Response headers** (observation from the same probes). The 200 and 429 responses of both deployments carry request IDs, model, deployment, cluster and region names and rate-limit counters. None of their values contains the subscription ID, the tenant ID, the signed-in user, the account's name, internal ID or principal ID or a resource path, and none sets a cookie, so cassettes store response headers as received.

**langchain-postgres 0.0.18.** Issue 337 and its fix, pull request 338, were both open on 2026-10-06. Line numbers refer to `langchain_postgres/v2/async_vectorstore.py` at 0.0.18.

- A search writes into the config it is given: `fetch_top_k` (line 719) and, when the keyword query is empty, the query text (lines 804 to 806). A test shows that 0.0.18 still writes the query into a shared config and fails once a later version stops doing so. With a config per call, two consecutive searches each use their own keyword query. A metadata filter constrains both legs.
- The keyword leg is `plainto_tsquery` (line 726), which requires every term to match; pull requests 268 and 339, both open, would relax this. Whatever produces the keyword string is therefore part of the retrieval path.
- The keyword leg orders by `ts_rank_cd` with no tie-breaker (line 733). Run directly on the loaded table (observation, 2026-10-06), 7 of the 30 keyword strings return rows with tied scores; the rank within a tie follows the order in which Postgres returns the rows.
- With a config whose keyword query is empty, the search skips the keyword leg and the fusion and returns the dense leg's 40 rows instead of `k` (lines 654 to 656 and 746). `retrieve` rejects an empty keyword string for that reason.
- Each leg runs on its own pooled connection (lines 708 and 734), so a transaction-scoped setting made by the caller does not reach either query. Row-level security for the corpus has to bind at the engine or pool level.
- Both legs select the embedding column (lines 661 to 665): a search fetches 80 vectors it does not use. The cost is latency only.

**Gate definition.** The gates were first stated on the pooled count and are stated on the mean per query. On this query set, 25 gate-strata queries with 26 expected IDs, one query holding two, the two definitions tolerate different numbers of missed expected IDs. Gate c (0.90): the pooled count needs 24 of 26 found, so it tolerates 2 misses; the mean needs the per-query recalls to sum to at least 22.5 over 25 queries, where a miss in a single-ID query costs 1.0 and a miss of one ID of the two-ID query costs 0.5, so it tolerates 3 misses when at least one of them is an ID of query 24 (one of its IDs and 2 in single-ID queries, or both of its IDs and 1 in a single-ID query), and 2 when all fall in single-ID queries. Gate d (0.85): the pooled count needs 23 of 26, so it tolerates 3 misses; the mean needs a sum of at least 21.25, so it tolerates 4 misses when at least one of them is an ID of query 24 (one of its IDs and 3 in single-ID queries, or both of its IDs and 2 in single-ID queries), and 3 when all fall in single-ID queries. Against the thresholds the mean per query is never harder to meet: it tolerates one more miss when at least one miss falls in the two-ID query, and the same number otherwise. Gate d's second condition, not below the fused top 5, compares two arms under one definition, and there the mean can be the harder one: a reranked top 5 that misses one single-ID query, against a fused top 5 that misses one ID of query 24, has the same pooled count, 25 of 26, but the lower mean, 0.96 against 0.98. This run's verdicts are the same under both: gate c has 25 of 26 found and a mean of 0.96, met under both; gate d after rerank has 22 of 26 found (0.846) and a mean of 0.84, not met under both.

The fourth, 1005.12(a)(1)(iv), was not among the twenty candidates: the keyword leg returned no row for its query and the dense leg ranked it 21st of its 40. The fourth was ranked 21st by the dense leg, inside its 40 rows and outside the twenty candidates, and the rule does not say at which depth the dense leg shows a paragraph to be retrievable: under the reading that the twenty candidates are that depth it does not count against the store, and under the stricter reading that any rank in the dense leg's rows is, the rule does not exclude it. Neither reading changes a decision of this record. The two levers were not run: neither can change the order after retrieval. All four are a lead-in or a list item: 1005.11(a)(1) and 1005.12(a)(1)(iv) end in a colon and leave their substance to the list items below them, and 1005.11(c)(2)(i)(A) and 1005.33(b)(1)(i) are list items without the sentence of their parent paragraph. That this parent/child granularity explains the misses is a hypothesis for the corpus step, not a finding.

**Second live run** (observation, 2026-10-06). The hybrid-with-keyword-string and rerank arm was run live a second time, in half a minute, with six rate-limit responses retried by the SDK. **Replay.** vcrpy applies the request filter to the live request before matching, and on one code path twice, so the filter leaves a body that is already a hash unchanged; matching uses vcrpy's built-in method, uri and body matchers, with no custom matcher. CI replays the run on linux/amd64 against the same database image, and the results-file test fails there if the replay does not reproduce the committed figures.

## Code written here

Each unit below is written in this repository because no component does its whole job, with one exception that its own line states: the manifest hash check. The analysis of the candidates is not kept here.

- **Comment IDs of Supplement I** (`ecfr.supplement_paragraphs`). Builds a comment's ID, `1005.11(c)-3`, from the heading it sits under and the order of the comment numbers in the flat XML, with three rules for defects in the source: a run of comments printed a second time under 32(b)(1) is dropped, the heading of 17(b)(3) that lost its tag is recovered from the end of the preceding paragraph, and the two comments printed as one paragraph under 20(c)(4) are split. The eCFR gives these comments no ids of their own; its rendered file repeats the same ids under every heading, so there is no identifier to read and the ID has to be rebuilt from the outline.
- **Regulation paragraph extraction** (`ecfr.parse_part`, `ecfr.regulation_paragraphs`). Reads each paragraph node of the renderer's HTML with the eCFR's own id, text and heading path, merges those paragraphs with the comments read from the XML, rejects an ID assigned twice and tags each paragraph's legal status by its source. The IDs and the hierarchy are the eCFR's and the HTML tree is the parser library's; splitters that work from headings yield records by heading or by text element and HTML partitioners one per text element, and neither carries the element's id, so none yields one record per paragraph node with that node's id.
- **Chunk text format** (`corpus.chunk_content`). Joins the paragraph ID, the heading path and the text into the one string that is embedded, keyword-indexed and reranked. A document formatter takes a template and fields that are already joined, which is this line again, and text splitters cut by size, which one chunk per paragraph does not need.
- **Manifest hash check** (`corpus.verified_manifest`, `corpus.read_corpus`). Refuses a snapshot file whose sha256 differs from the manifest before anything is embedded or loaded, and refuses a load when any of the four snapshot files is missing from the manifest; the hashing is the standard library's. pooch 1.9.0 can do this check: built with `allow_updates=False` and a registry of the manifest's file names and hashes, it raises on a file that differs and on a name the registry does not list. It is not adopted: the check stays on the standard library, and the switch is left as a later change.
- **Snapshot download** (`corpus_build.fetch`). Fetches the part as XML and as rendered HTML, following the renderer's redirect, and starts the manifest with the URL each file was fetched from, the latest amendment date and the reason for the pin; the HTTP client is a library. A download tool checks a given hash and keeps a cache; it records neither the final URL nor those fields.
- **Table load** (`corpus.load`). The table and the insert are the vendor's; the mapping of the chunk fields to the typed columns and the row IDs, `uuid5(snapshot:paragraph_id)`, are written here.
- **Writing of the corpus files** (`corpus_build.embed_corpus`, `corpus_build.write_manifest`). Writes the chunk file, the vector file and the manifest fields: the sha256 of each file, the chunk counts by source, the parser and content-format versions and the embedding model, deployment version, dimensions and dtype. The serialisation is the standard library's and numpy's; the layout and the fields are this snapshot's record, which no component writes.
- **Settings and model client construction** (`foundry.py`). The settings class is the settings library's and the clients are the vendor classes; written here are a validator that strips the endpoint's trailing slash and the clients' arguments: the key or the token provider passed as the API key, because the model classes drop the timeout and the retry count when given a token credential; the explicit timeout on every client; and the rerank client's retry count, because the SDK's header parser never waits on the `retry-after-ms` the rerank route sends.
- **Rerank index mapping** (one line in `retrieval.rerank`). Maps the index and score the rerank API returns back to the candidate documents; the API returns nothing else, and the installed model integration has no reranker.
- **The seams `embed`, `retrieve` and `rerank`, and the blank-keyword guard** (`retrieval.py`). Each seam is one vendor call with this project's arguments. The guard rejects an empty or blank keyword string: given an empty one, the vendor skips the keyword leg and the fusion and returns the dense leg's rows in place of `k` candidates, and given a blank one, the keyword leg runs a query with no terms and returns no rows.
- **Request-body hash in recorded responses** (`tests/conftest.py`). Replaces each request body in a cassette with the sha256 of its canonical JSON, so that cassettes hold no query or regulation text while the body matcher still tells requests apart. The recording library has no hashing. Its body filter can pass a named top-level field to a callable, which could hash it, but that callable would still be written here, a field that is not named is recorded in plain text, and only POST bodies sent as exactly `application/json` are parsed.
- **Dropping a recorded rate-limit response** (`tests/conftest.py`). Returns nothing from the recording library's response hook for a 429, so that a call the SDK retried is stored as the response that succeeded. The library records every response and filters by status nowhere; the hook is its extension point.
- **Keyword-leg observation in the exit test** (`tests/test_exit.py`). Wraps the fusion function to read the rows of the keyword leg, which the vendor passes to that function and exposes nowhere else.
- **The recall@k metric class, the five-arm loop and the mean over queries** (`tests/test_exit.py`). The metric class hands each query's expected and retrieved IDs to ir-measures and returns its `R@k`; the loop runs the five arms over the query set; the figure for a set of queries is the standard library's mean. The evaluation framework's own recall metrics are judged by a model, and no framework runs these arms.
- **Results generation** (`tests/test_exit.py`). Aggregates the library output into the results file: the rank of each expected ID in each arm, rescued and lost IDs, and the counts with their intervals from scipy. No measure of the retrieval-evaluation library gives the rank of each expected ID (reciprocal rank gives only the first relevant one), a rescue or a loss.
- **Vendor configuration and test code.** The search configuration (`retrieval.hybrid_config`, `retrieval.open_store`), the recording configuration and the DeepEval switches (`tests/conftest.py`), the Terraform roots (`infra/bootstrap`, `infra/foundry`), the CI workflow apart from its phrase scan (`.github/workflows/ci.yml`), the fixtures and the test bodies. They configure vendor components and test this repository's own code; there is nothing in them for a component to replace.
- **The banned-phrase scan in CI, and the smoke script with its dimension check, the readback script and the command lines** (`.github/workflows/ci.yml`, `foundry_smoke.py`, `infra/foundry/readback.sh`, `corpus_build.main`, `foundry_smoke.main`). The scan reads commit messages and annotated tag bodies as well as file and history content outside `corpus/`; the secret scanner's rules reach file and history content only. The smoke script makes one live call per deployment through this project's clients and checks the embedding dimensions, which no vendor command does; the readback is four Azure CLI calls, and the command lines are the standard library's argument parser.

## Consequences

- Gate d stays not met until the next configuration is measured. On this query set, retrieval through this path delivers every expected paragraph in the top 5 for 21 of 25 gate-strata queries (22 of 26 expected IDs), and later steps are built on that figure, whose 95% interval is 0.65 to 0.94, not on the threshold.
- Gates fixed before a later run are written with these points, which do not change this result:
  - A comparison between two arms is paired and carries a stated non-inferiority margin; a comparison of two point values is decided by one query.
  - Store gates are kept apart from rerank-stage gates, and the flip trigger is the operative rule for the store.
  - The relevance policy for hierarchical paragraphs is defined before the labels are written.
  - A clause over "every stratum" names what it means for a stratum without a target; the clause on the optional keyword leg did not, for the citation stratum.
- The citation check and every later step depend on the paragraph IDs. A move of the pin, a parser change or a content-format change produces new chunk files, a new embedding run of about half an hour at the current quota, and new cassettes.
- Regulation IDs depend on the renderer endpoint, which the eCFR does not document. The file is stored with its sha256, so the pinned text stays reproducible without the endpoint; a change in the endpoint's markup shows at the next refresh, where the parser raises or the snapshot tests fail.
- Rate limits are handled by SDK retries alone. An embedding run takes as long as the tokens-per-minute quota allows, and a rate limit that outlasts the retries fails the run; it is not paced around in this repository's code.
- Hybrid search adds to dense search only when the caller supplies a keyword string. Whatever produces that string for a live query becomes part of the retrieval path and has to be measured with it.
- The per-call `HybridSearchConfig` stays until a langchain-postgres release stops mutating the config; the test that detects that release names what to review.
- The corpus row-level security has to be set on the engine or its pool, because the vendor's searches do not run inside the caller's transaction.
- A dependency update that changes a request body fails the recorded tests until the cassettes are recorded again, which needs the Foundry account, the Azure CLI login and the database, and about three minutes for the exit test at the current rerank quota. An update of deepeval, ir-measures, pytrec-eval-terrier, scipy or langchain-postgres changes the versions in the results file, so the results test fails until the file is generated again.
- pytrec-eval-terrier stays a test-only dependency; using trec_eval in the service itself would need its licence terms settled first.
- The database image is updated by hand when the versions offered by Azure Database for PostgreSQL change.

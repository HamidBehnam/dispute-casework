# ADR 0004: Retrieval store

Status: Accepted. Superseded in part by 0005 and 0006.

## Context

Every citation the agent makes is a paragraph ID of Regulation E that must have been retrieved. The design puts hybrid retrieval in the application's Postgres through the pinned LangChain Postgres package, with a reranker as a second stage and Qdrant as the recorded fallback store. The spike had to show, on the real regulation text, that the eCFR text yields stable paragraph IDs, that hybrid search in langchain-postgres 0.0.18 works when configured explicitly, what each stage contributes on a hand-written query set, and that the path can be tested offline.

Two rules bound the answer: every AI capability is a vendor or framework component, and code is written here only where no component does the whole job, each such unit listed under "Code written here"; and the paragraph IDs of regulation text are the eCFR's own.

The following were fixed before the run recorded here.

- **Query set.** 30 hand-written queries in three strata: bare citations, exact-term queries and paraphrased questions, each with its expected paragraph IDs and a keyword string of three to five terms (the ID itself for a citation).
- **Arms.** Dense search; hybrid search with the question as the keyword query; hybrid search with the keyword string; dense search with rerank; hybrid search with the keyword string and rerank. Rerank takes the arm's twenty candidates and returns five.
- **Recall.** Recall@k of a query is the share of its expected paragraph IDs among the first k results, computed per query by ir-measures 0.4.3 as `R@k` (trec_eval's `recall_k` through pytrec-eval-terrier 0.5.10). The figure for a set of queries is the mean of the per-query values, each query counting the same, taken with the standard library's `fmean`. The pooled count, expected IDs found over expected IDs (`NumRelRet` over `NumRel` on the run cut to k), is reported beside it and is not gated.
- **Gates.** They apply to the exact-term and paraphrased strata (the gate strata). The citation stratum is measured and reported, never gated, because an exact citation is served by the citation lookup in the design.
  - a. Two consecutive searches each use their own keyword query.
  - b. With keyword strings, the keyword leg returns rows for at least 90% of gate-strata queries (23 of 25).
  - c. Recall@20 of hybrid search with keyword strings is at least 0.90.
  - d. Recall@5 of hybrid search with keyword strings after rerank is at least 0.85 and not below recall@5 of the same arm's fused top 5.
  - e. One live double run of the hybrid and rerank arm returns the same top 5; reported, not gated.

  The 25 gate-strata queries include one with two expected IDs, so the mean moves in steps of 0.02: gate c is met from 0.90 and gate d from 0.86.

  The gates were first stated on the pooled count. The definition was changed to the mean per query, with the thresholds unchanged, after an earlier run under the pooled definition had been measured and before the run recorded here; on that earlier run both definitions give the same verdict on every gate.
- **Fault attribution.** A failed check counts against the store only if the dense leg alone shows the paragraph to be retrievable. Parser, chunking and label faults are fixed in code and do not count against the store.
- **Levers.** `rrf_k`, and the text-search language constant with a table rebuild. A custom fusion function, hand-written keyword SQL and merging in Python are excluded.
- **Flip trigger.** The store moves to Qdrant only if hybrid search with keyword strings has a lower recall@20 than dense search on the exact-term stratum and a bounded sparse-hybrid run on Qdrant beats it on the same queries.
- **Keyword leg.** If dense search with rerank meets the targets on every stratum, the keyword leg is recorded as optional.
- **Statistics.** Every figure is generated by code from the replayed run into `docs/results/0004-exit-run.json`, and a test fails when that file is not what the recorded run produces. Statistics come from scipy only. The interval for a cell is `scipy.stats.binomtest(queries whose recall@k is 1.0, queries in the cell).proportion_ci(method="wilson")` at the 95% level, labelled as the share of queries with every expected ID found. The reranked top 5 is compared with the fused top 5 by query: the number of queries where rerank is higher and where it is lower, and `scipy.stats.binomtest(higher, higher + lower, 0.5)` when at least one query differs. There is no bootstrap and no interval on a pooled count. A non-significant test is not evidence that rerank is no worse.
- **Live sessions.** The vectors and the recorded responses come from two sessions on the Foundry account, under the Azure CLI login, with the deployments as they are: no capacity or deployment change is made for them, and no wait is added in this repository's code. Session logs stay outside the repository.
  - *Embedding session* (deployment limits: 10,000 tokens a minute and 10 requests per 10 seconds). Response headers are captured with an httpx response hook on a client passed to the same model class, or through the SDK's raw-response access if the hook does not fire. Probes first: one smoke call; one request of 16 chunks; then the first 96 chunks as six requests back to back, recording for the first 429 its headers, its error code, the SDK's retry line and whether the retry returned 200; then a 90-second wait. Stage 1 is the client as configured, on the SDK's default retries, in one embed call over all 1,742 contents. It passes if it completes without an exception, every request ends in a 200, every 429 is followed by a 200 for the same request, `embeddings.npy` is (1742, 1536) float32 and the manifest verifies. Stage 2 runs only if stage 1 fails: the same call with `max_retries` set to the larger of 6 and 75 divided by w, rounded up and capped at 40, where w is the number of seconds the SDK waited before its first retry in stage 1; it is skipped if stage 1 shows the SDK declining to retry because the server's retry-after exceeds its maximum. The files of the stage that passes become the committed snapshot, and the token-count batching and the pacing written here are deleted; `max_retries` appears in the code only if stage 2 is the stage that passed. If neither passes, the run stops there. The new vectors are checked against the previous ones on the chunks whose content is byte-identical in both snapshots: `numpy.testing.assert_allclose(new, old, rtol=0, atol=0.01)`.
  - *Rerank session* (deployment limits: 20,000 tokens a minute and 20 requests a minute). One 20-candidate call through the SDK's raw-response access records the response header names, any rate-limit values and the billed search units. After at least 90 seconds without a call, one fixed request (the twenty hybrid candidates of the first paraphrased query) is sent with `max_tokens_per_doc=512`, back to back with retries off, until the first 429 or 25 calls; after another 90 idle seconds the same request is sent without `max_tokens_per_doc`. The cap is removed unless the uncapped request is rejected or its series reaches the first 429 two or more calls earlier than the capped series. If the 429 carries a header the cohere SDK waits on (an integer or HTTP-date `retry-after`, or `x-ratelimit-reset`), the recording runs on the SDK's default retries; otherwise the SDK's own retry count on the client is raised to 7. The three cassettes are then recorded once; the recording passes if the tests pass with gate d as measured and the cassettes hold only 200s. The hybrid and rerank arm is then run live a second time for gate e and its top 5 and twenty candidates are compared per query with the recorded run; that comparison is an observation, not a recording.

## Decision

- **Store.** PostgreSQL with pgvector through langchain-postgres 0.0.19 stays. The flip trigger did not fire: on the exact-term stratum hybrid search with keyword strings has the same recall@20 as dense search, so no Qdrant run was made (`strata."exact-term".arms.hybrid_keyword.recall_at_20` and `strata."exact-term".arms.dense.recall_at_20` in `docs/results/0004-exit-run.json`). The store stays by the rule fixed before the run, not on evidence that hybrid search raises recall@20: the two arms are also equal on the gate strata (the same keys under `strata."gate strata"`). The pin is 0.0.19.
- **Gate d.** Not met, as measured: on the gate strata recall@5 after rerank is under the threshold of 0.85 and under recall@5 of the fused top 5 (`strata."gate strata".arms.hybrid_keyword_rerank.recall_at_5` against `strata."gate strata".arms.hybrid_keyword.recall_at_5` in `docs/results/0004-exit-run.json`). The thresholds, the chunking, the labels and the recorded run are left as they are. The exit test carries gate d as a strict expected failure that fails the suite once the gate is met.
- **Corpus pin.** Regulation E is pinned to the eCFR text of 2023-04-19, the date of the last Part 1005 amendment in force; later versions carry the amendments of 89 FR 106768, which Public Law 119-10 (May 9, 2025) disapproved before they took effect. The snapshot is labelled "unofficial eCFR snapshot" because the eCFR is not an official legal edition of the CFR. Appendices A to C are deferred to the corpus step, where the model forms get the legal status `model_form`.
- **Refresh rule.** List the amendment dates since the pin from the versioner, read each amending Federal Register document, and check for a Congressional Review Act disapproval. The pin moves only if every amendment it brings is in force.
- **Corpus source.** The regulation's paragraph IDs, text and hierarchy come from the eCFR's renderer output, `https://www.ecfr.gov/api/renderer/v1/content/enhanced/<date>/title-12?part=1005`, which redirects to the same content addressed by chapter; the manifest records the URL as fetched. The endpoint is outside the eCFR's published API specification; its identifiers are the anchors of the public eCFR pages. Supplement I is read from the versioner XML.
- **Paragraph IDs.** The ID of a regulation paragraph is the id of its node in the eCFR's file, verbatim, without the `p-` prefix; a paragraph directly inside a section takes the section's id. The comments of Supplement I, which the eCFR gives no ids, keep the IDs the comment parser assigns from the XML; `1005.A-1` for comments on Appendix A is provisional until the corpus step. Three source defects have their own rules: the second printing of comments 2 to 7 under 32(b)(1) is dropped, the heading of 17(b)(3) that lost its tag is recovered from the preceding paragraph, and comments 1 and 2 under 20(c)(4), printed as one paragraph, are split. Regulation text is `binding`, Supplement I `official_interpretation`.
- **Chunking.** One chunk per paragraph: the paragraph ID, the heading path and the text on three lines (content format 1), the same string embedded, keyword-indexed and reranked.
- **Embeddings.** text-embedding-3-large at 1536 dimensions, generated once into a float32 `.npy` file row-aligned with `chunks.jsonl`, by one embed call sending 16 raw strings a request. Rate limits are left to the SDK's retries at langchain-openai's default of two; nothing here batches by token count or waits. The files are in plain git; Git LFS starts with the first file over about 50 MB.
- **Table.** Exact search, cosine distance, `PGVectorStore` on the psycopg 3 driver. The vendor's `init_vectorstore_table` creates `chunks` with typed metadata columns, a stored `content_tsv` column in `pg_catalog.english` and no index at this size; row IDs are `uuid5(snapshot:paragraph_id)`. An explicit step loads it after the manifest hashes verify.
- **Hybrid search.** Every search builds a new `HybridSearchConfig`: the stored tsvector column, reciprocal rank fusion with `rrf_k` 60, 40 rows per leg, and `k` 20 candidates passed explicitly because the vendor overwrites `fetch_top_k` with `k`. The keyword query is a separate short string; `retrieve` raises `ValueError` when it is empty or blank. The text-search language is one constant applied at insert and at query.
- **Rerank.** Cohere-rerank-v4.0-fast through the existing client, top 5, with no `max_tokens_per_doc`, the explicit 60-second timeout and `max_retries=7`, for the reasons under Rerank session.
- **Database image.** `pgvector/pgvector:0.8.2-pg17`, pinned in `compose.yaml` by the digest of its multi-platform image index and used by CI through `docker compose`. The pin follows the versions Azure Database for PostgreSQL offers, so it is not on the dependency update bot.
- **Recorded responses.** pytest-recording 0.13.4 on vcrpy 8.3.0, record mode `none`, network blocked by default; request bodies stored as their sha256, response headers as received, rate-limit responses dropped. For this step the recorded embedding response is the cache of query embeddings; an evaluation set of real size will want a plain file.
- **Evaluation tooling.** Recall@k is computed by ir-measures 0.4.3 inside a DeepEval 4.2.8 metric class that DeepEval's `evaluate()` runs; statistics come from scipy 1.18.1. ir-measures calls trec_eval through pytrec-eval-terrier 0.5.10, which compiles trec_eval 9.0.8 sources whose file headers read "research, non-commercial purposes"; it is a test-only dependency and no part of it ships with the service. DeepEval is used as a library, switched off before import and kept out of pytest's plugins. The recall metric is deterministic and could be computed by ir-measures alone; it runs inside DeepEval so that later evaluation steps run the same metric beside their model-judged ones, at the cost of the dependencies and the switches this record lists.
- **Next configuration.** Fixed here for the corpus step, in this order: the label policy for lead-in and parent/child paragraphs is settled first as a domain question (which paragraph is the correct citation); then a chunking rule decidable from the source files alone, under which lead-ins and list items carry their context, is applied to every chunk and label; the corpus is embedded again as a new configuration under its own tag and evaluated on new queries written after the rule; and the result below is kept beside the new one.

## Findings

The exit run was recorded on 2026-10-06 against PostgreSQL 17.10 with pgvector 0.8.2, SQLAlchemy 2.1.1 and psycopg 3.3.6. Its figures are in `docs/results/0004-exit-run.json`, which a test regenerates from the recorded responses. An observation comes from a named live session and is not reproduced by a test.

**Corpus** (counted from the committed snapshot files; not in the results file). The versioner XML is 858,281 bytes and the renderer HTML 1,401,436 bytes; the versioner reports 2023-04-19 as the latest amendment date. The renderer file has 27 sections with 834 paragraph nodes; 96 hold only a designator and a heading, and three sections open with a paragraph that takes the section's id, which leaves 741 regulation chunks. Supplement I has 1,012 paragraph elements, 1,013 comments once the two under 20(c)(4) are split and 1,001 once the 12 of the second run under 32(b)(1) are dropped: 1,742 chunks with unique IDs and, with the provisional `1005.A`, 28 distinct section values. `embeddings.npy` is 10.7 MB.

**Embedding session** (observations, 2026-10-06, Azure CLI login). The probes met no rate limit; a request of 16 chunks returned 200 with `x-ratelimit-limit-tokens: 10000`. Stage 1 passed: one embed call over the 1,742 contents made 109 requests, each ending in a 200, in 29.5 minutes; 50 responses were a 429, each followed by a 200 on the SDK's first retry after a wait of 1 to 59 seconds. Stage 2 was not run and no `max_retries` is set. A later probe of twelve back-to-back requests through a client with a response hook, not among the steps fixed before the run, captured a 429 with `retry-after: 56` and `x-ratelimit-reset-tokens: 56`, no `retry-after-ms` and error code `RateLimitReached`; the SDK logged "Retrying request in 56.000000 seconds (retry 1 of 2)" and the retry returned 200. On the 1,648 chunks whose content is byte-identical in the previous snapshot, the new vectors pass `assert_allclose(new, old, rtol=0, atol=0.01)`; the largest absolute difference in a component is 0.0092.

**Rerank session** (observations, 2026-10-06, Azure CLI login). One 20-candidate call returned 200 with `x-ratelimit-limit-requests: 20` and `x-ratelimit-limit-tokens: 20000`, renewed every 60 seconds. The fixed request sent back to back reached its first 429 on call 23 with `max_tokens_per_doc=512` and, after 90 idle seconds, without it, with the same top 5 and one search unit billed a call, so the cap is removed. Both 429s carry `retry-after-ms` (302 and 381) and `x-ratelimit-reset-requests: 60`, no `retry-after`, and error code `RateLimitReached`. cohere 7.2.0 waits on an integer or HTTP-date `retry-after` or on `x-ratelimit-reset`; it looks up `retry-after-ms` but never waits on it, because its parser compares the header string with a number and discards the `TypeError`. It backs off exponentially from one second, so the client's retry count is raised from the SDK's default of 2 to 7. The cassettes were then recorded once on those retries; the exit cassette holds two embedding requests and 60 rerank calls, and the 55 rate-limit responses the SDK retried are not stored.

**Response headers** (observation from the same probes). `docs/architecture.md` states what the 200 and 429 responses carry; they also carry cluster names, and none carries a user or resource identifier.

**langchain-postgres 0.0.19.** Line numbers refer to `langchain_postgres/v2/async_vectorstore.py`. The pin is the vendor's patched release for its repository advisory GHSA-39qm-gv6q-f43r (high; vulnerable range >=0.0.14rc1,<0.0.19), which is published on the vendor's repository and is in neither the global advisory database nor OSV, so pip-audit and Dependabot alerts do not surface it; the inline-embedding path the advisory concerns is not reached here, since the store's constructor refuses only an embedding service that has `embed_query_inline` without `embed_query_inline_template` (lines 122 to 130) and neither embedding class handed to the store has either attribute. Issue 337 and its fix, pull request 338, are open on 2026-10-27.

- A search writes into the config it is given: `fetch_top_k` on every hybrid search whose keyword query is non-empty (the condition at line 718, the write at line 719) and, on the text-search path with an empty keyword query, the query text (lines 803 to 805); `retrieve` searches by vector, where only `fetch_top_k` is written. A test shows that 0.0.19 does so and fails once a later version stops. With a config per call, two consecutive searches each use their own keyword query; a metadata filter constrains both legs.
- The keyword leg is `plainto_tsquery` (line 726), which requires every term to match; pull requests 268 and 339, both open, would relax this. Whatever produces the keyword string is therefore part of the retrieval path.
- The keyword leg orders by `ts_rank_cd` with no tie-breaker (line 733); on the loaded table (observation, 2026-10-06), 7 of the 30 keyword strings return tied scores, ranked in the order Postgres returns the rows.
- With an empty keyword query the search skips the keyword leg and the fusion and returns the dense leg's 40 rows instead of `k` (lines 659 to 661 and 746), which is why `retrieve` rejects it.
- Each leg runs on its own pooled connection (lines 708 and 734), so a transaction-scoped setting of the caller reaches neither query; row-level security for the corpus has to bind at the engine or pool level.
- Both legs select the embedding column (lines 666 to 670), so a search fetches 80 vectors it does not use; the cost is latency only.

**Exit test.** 30 queries: 5 bare citations, 9 exact-term queries and 16 paraphrased questions (`strata.<stratum>.queries`); one paraphrased query has two expected IDs, so the 25 gate-strata queries have 26 (`strata."gate strata".queries` and `strata."gate strata".expected_ids`). Recall@5 of the three search arms is taken on the first five of their twenty candidates. Dense search with rerank has the same recall@5 on the gate strata (`strata."gate strata".arms.dense_rerank.recall_at_5`) and misses the same expected IDs (`queries[].ranks.<paragraph_id>.dense_rerank` for the IDs under `missed_after_rerank`).

**Gate definition.** Under the pooled count (`found` over `expected` in `recall_at_20` and `recall_at_5`) this run's verdicts on gates c and d are the same as under the mean per query.

**Sample size.** The interval is on the share of queries with every expected ID found, which on the gate strata differs from the mean recall only through the one query with two expected IDs; every cell's interval is its `share_of_queries_with_every_expected_id_interval`, at the level in `method.confidence_level`, and the one later steps build on is under `strata."gate strata".arms.hybrid_keyword_rerank.recall_at_5`. The interval treats the queries as independent; the set was written by hand, and 15 of its 25 gate-strata queries, counted from the expected IDs in `tests/queries.json`, have an expected ID in § 1005.11 or its official interpretation, so it likely understates the uncertainty. The per-stratum figures are descriptive only.

**Gate d.** The expected IDs missing from the reranked top 5 are listed under `missed_after_rerank`, each with its `query` number, its `rank_in_fused_twenty` and its `rank_in_dense_top_40`.

Those with a rank in the fused twenty were among the candidates the store returned, so their miss lies in the order after retrieval and does not count against the store; the two levers were not run. The one without (`rank_in_fused_twenty` null) sits inside the dense leg's 40 rows and outside the twenty candidates (`rank_in_dense_top_40`), where the fault-attribution rule does not name a depth: under the reading that the twenty candidates are that depth it does not count against the store, under the reading that any rank in the dense leg's rows is, the rule does not exclude it, and neither reading changes a decision of this record. All of them are a lead-in or a list item; that this granularity explains the misses is a hypothesis for the corpus step, not a finding. The second clause of gate d compares two point values which one query decides: under `strata."gate strata".arms.hybrid_keyword_rerank.against_first_five_before_rerank`, `lower` exceeds `higher` by one.

**Reranker.** By query, recall@5 after rerank against recall@5 of the same arm's first five candidates: `higher`, `lower` and `p_value` under `against_first_five_before_rerank` of `hybrid_keyword_rerank` and of `dense_rerank` in each stratum; on the gate strata neither test is significant. A non-significant test is not evidence that rerank is no worse: with so few differing queries the test cannot show a difference of this size either way, so the data supports neither that rerank lowers recall nor that it meets the 0.85 threshold. On the citation stratum rerank of the hybrid arm puts the expected paragraph first for every query (`hybrid_keyword_rerank` in `queries[].ranks` for the citation queries).

**Keyword leg.** On the gate strata the keyword leg returns rows for few queries given the question as written, and for none of the paraphrased questions, but for nearly every query given the keyword string (`keyword_leg_non_empty` of `hybrid_raw` and `hybrid_keyword` under `strata."gate strata"` and `strata.paraphrased`); there it rescued no expected ID at 20 (`hybrid_keyword.rescued` is empty), and the fused top 5 is above dense search's (`hybrid_keyword.recall_at_5` against `dense.recall_at_5`). On the citation stratum, with keyword strings, it rescued most of the expected IDs, which dense search mostly misses (`strata.citation.arms.hybrid_keyword.rescued` and `strata.citation.arms.dense.recall_at_20`). The keyword strings were written by hand before the run, and the figures hold for those strings; what strings generated by the triage stage would score is not measured here. The keyword leg is not recorded as optional, because dense search with rerank does not meet the gate d target. The clause over "every stratum" does not say what it means for the citation stratum, which has no target.

**Per query.** Each entry of `queries` carries the query's `number` and `stratum`, the rank of each expected ID in each arm under `ranks.<paragraph_id>.<arm>`, and the keyword leg's row counts under `keyword_leg_rows.raw_question` and `keyword_leg_rows.keyword_string`.

**Second live run** (observation, 2026-10-06). The hybrid-with-keyword-string and rerank arm was run live a second time, in half a minute, with six rate-limit responses retried by the SDK. The reranked top 5 was identical to the recorded run for 30 of 30 queries; the twenty candidates were identical, in order, for 29 of 30, and for query 3 the same twenty came back in another order. 10 of the 30 query vectors differed between the two embedding calls, by at most 0.0005 in a component, which is why CI replays the recorded ones. In the recorded run 2 of the 60 rerank responses, counted from the rerank responses in the exit cassette `tests/cassettes/test_exit/test_exit_gates.yaml`, hold two equal relevance scores in their top 5.

**Replay.** vcrpy applies the request filter to the live request before matching, on one code path twice, so the filter leaves a body that is already a hash unchanged; matching uses vcrpy's built-in method, uri and body matchers. CI replays the run on linux/amd64 against the same database image.

## Code written here

Each unit is written here because no component does its whole job.

- **Comment IDs of Supplement I** (`ecfr.supplement_paragraphs`): builds a comment's ID from its heading and the order of the comment numbers in the flat XML, with the three source-defect rules under Paragraph IDs; the eCFR gives these comments no ids, and its rendered file repeats the same ids under every heading.
- **Regulation paragraph extraction** (`ecfr.parse_part`, `ecfr.regulation_paragraphs`): reads each paragraph node of the renderer's HTML with the eCFR's own id, text and heading path, merges in the comments, rejects an ID assigned twice and tags legal status by source; heading-based splitters and HTML partitioners yield records without the element's id.
- **Chunk text format** (`corpus.chunk_content`): joins the paragraph ID, the heading path and the text into the one string that is embedded, keyword-indexed and reranked; a document formatter needs the fields already joined, and text splitters cut by size.
- **Manifest hash check** (`corpus.verified_manifest`, `corpus.read_corpus`): refuses a snapshot file whose sha256 differs from the manifest, a load when a snapshot file is missing from the manifest, and a listed file that is missing on disk, each before the table is touched and with the standard library's hashing and file reads. pooch 1.9.0, built with `allow_updates=False` and a registry of the manifest's names and hashes, raises in the first two cases but downloads a listed file that is missing on disk, and it has no call that only verifies the local files against its registry: `Pooch` exposes `fetch`, `is_available`, which asks the remote, `get_url`, `load_registry`, `load_registry_from_doi`, `registry_files` and `abspath`, and `hashes.hash_matches` compares one file with one given hash.
- **Snapshot download** (`corpus_build.fetch`): fetches the part as XML and as rendered HTML, following the renderer's redirect, and starts the manifest with the URL each file was fetched from, the latest amendment date and the reason for the pin; a download tool checks a hash and keeps a cache but records none of those fields.
- **Table load** (`corpus.load`): maps the chunk fields to the typed columns and sets the row IDs `uuid5(snapshot:paragraph_id)`; the vendor's indexing API embeds again through `add_documents`, needs a record manager, and takes each row ID from a `key_encoder` callable or else from its own hash of the content and the metadata.
- **Writing of the corpus files** (`corpus_build.embed_corpus`, `corpus_build.write_manifest`): writes the chunk file, the vector file and the manifest fields with the standard library and numpy; no component writes this snapshot's layout.
- **Settings and model client construction** (`foundry.py`; the pydantic-settings classes are `foundry.FoundrySettings` and `database.DatabaseSettings`): the validator that strips the endpoint's trailing slash and the clients' arguments on the vendor classes, the key or token provider passed as the API key, the explicit timeout and the rerank retry count, for the reasons in ADR 0003 and `MODELS.md`; no component supplies these arguments.
- **Rerank index mapping** (one line in `retrieval.rerank`): maps the index and score the rerank API returns back to the candidate documents; the API returns nothing else, and the installed model integration has no reranker.
- **The seams `embed`, `retrieve` and `rerank`, and the blank-keyword guard** (`retrieval.py`): each seam is one vendor call with this project's arguments; the guard rejects an empty or blank keyword string because the vendor returns the dense leg's rows for an empty one and no keyword rows for a blank one.
- **Request-body hash in recorded responses** (`tests/conftest.py`): replaces each request body in a cassette with the sha256 of its canonical JSON, so cassettes hold no query or regulation text while the body matcher still tells requests apart; the recording library has no hashing, and its body filter leaves unnamed fields in plain text.
- **Dropping a recorded rate-limit response** (`tests/conftest.py`): returns nothing from the recording library's response hook for a 429, so a call the SDK retried is stored as the response that succeeded; the library records every response and filters by status nowhere.
- **Keyword-leg observation in the exit test** (`tests/test_exit.py`): wraps the fusion function to read the rows of the keyword leg, which the vendor exposes nowhere else.
- **The recall@k metric class, the five-arm loop and the mean over queries** (`tests/test_exit.py`): hands each query's expected and retrieved IDs to ir-measures and returns its `R@k`, runs the five arms and takes the standard library's mean of the per-query values; `ir_measures.calc_aggregate` over all queries returns the same mean, but the metric runs one query at a time inside the evaluation framework, whose per-query values the interval and the rerank comparison need; the framework's own recall metrics are judged by a model, and no framework runs these arms.
- **Results generation** (`tests/test_exit.py`): aggregates the library output into the results file, the rank of each expected ID in each arm, rescued and lost IDs, and the counts with their intervals from scipy; no measure of the retrieval-evaluation library gives a rank per expected ID, a rescue or a loss.
- **Vendor configuration and test code** (`retrieval.hybrid_config`, `retrieval.open_store`, `tests/conftest.py`, `infra/bootstrap`, `infra/foundry`, `.github/workflows/ci.yml`, the fixtures and the test bodies): configures vendor components and tests this repository's own code; there is nothing in them for a component to replace.
- **The smoke script with its dimension check, the readback script and the command lines** (`foundry_smoke.py`, `infra/foundry/readback.sh`, `corpus_build.main`, `foundry_smoke.main`): the smoke script makes one live call per deployment through this project's clients and checks the embedding dimensions, which no vendor command does; the readback is four Azure CLI calls and the command lines are the standard library's argument parser.

## Rationale

- **What it does.** Retrieval runs the vendor's hybrid search in the application's Postgres — pgvector cosine distance on one leg, a stored tsvector column on the other, fused by reciprocal rank fusion into a fixed candidate set — and a Cohere reranker orders that set and keeps the top five. Each candidate is one paragraph of Regulation E or its official interpretation under its citation ID, so that the citation check of a later step can hold every citation to a retrieved ID.
- **What it changed and cost.** The step added a pinned, hash-verified eCFR snapshot with its own paragraph parser, one committed embedding run, an exit test that replays recorded model responses in CI, and a per-call hybrid-search configuration that works around the config mutation in the pinned langchain-postgres release. It cost one embedding session and one rerank-recording session under the deployments' rate limits, and it leaves gate d unmet: recall@5 after rerank is under its threshold and under the fused top five, as recorded in `docs/results/0004-exit-run.json`.
- **Why this over the alternative.** PostgreSQL with pgvector stays because the flip trigger fixed before the run did not fire — hybrid search with keyword strings equalled dense search at recall@20 on the exact-term stratum — and no index is needed at this row count. One chunk per eCFR paragraph because the citation unit is the paragraph ID, which no splitter or partitioner preserves; the reranker stays as the designed second stage, with its effect on the gate strata undetermined on this query set and re-measured at the next configuration.

## Consequences

- Gate d stays not met until the next configuration is measured. On this query set, retrieval through this path delivers every expected paragraph in the top 5 for most gate-strata queries, and later steps are built on that figure and its interval, `queries_with_every_expected_id` and `share_of_queries_with_every_expected_id_interval` under `strata."gate strata".arms.hybrid_keyword_rerank.recall_at_5`, with the pooled count `found` over `expected` beside them, not on the threshold.
- The citation check and every later step depend on the paragraph IDs. A move of the pin, a parser change or a content-format change produces new chunk files, an embedding run of about half an hour at the current quota, and new cassettes.
- Regulation IDs depend on the renderer endpoint, which the eCFR does not document. The file is stored with its sha256, so the pinned text stays reproducible without the endpoint; a change in its markup shows at the next refresh, where the parser raises or the snapshot tests fail.
- The retry counts and the absence of a rerank cap rest on the live sessions under Findings. An embedding run takes as long as the tokens-per-minute quota allows, and a rate limit that outlasts the SDK's retries fails the run.
- Hybrid search adds to dense search only when the caller supplies a keyword string. Whatever produces that string for a live query becomes part of the retrieval path and has to be measured with it.
- The per-call `HybridSearchConfig` stays until a langchain-postgres release stops mutating the config; the test that detects that release names what to review.
- The corpus row-level security has to be set on the engine or its pool, because the vendor's searches do not run inside the caller's transaction.
- A dependency update that changes a request body fails the recorded tests until the cassettes are recorded again, which needs the Foundry account, the Azure CLI login and the database. An update of deepeval, ir-measures, pytrec-eval-terrier, scipy or langchain-postgres changes the versions in the results file, so the results test fails until the file is generated again.
- pytrec-eval-terrier stays a test-only dependency; using trec_eval in the service itself would need its licence terms settled first.
- The database image is updated by hand when the versions offered by Azure Database for PostgreSQL change.

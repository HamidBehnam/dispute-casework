# ADR 0006: Model clients through langchain-openai

Status: Accepted. Supersedes 0003 in part: in its Decision, the sentence "Python: the direct dependencies for model access are langchain-azure-ai 1.2.10, azure-identity 1.25.3, cohere 7.2.0, pydantic 2.13.5 and pydantic-settings 2.15.0, at the versions in `uv.lock`." and the two sentences "Chat models are `AzureAIOpenAIApiChatModel` on `<endpoint>/openai/v1`, on the Responses API for OpenAI models and on chat completions for DeepSeek. Embeddings are `AzureAIOpenAIApiEmbeddingsModel` at 1536 dimensions with 16 inputs a request."; in its Rationale, "langchain-azure-ai over langchain-openai directly: one credential type across chat, embeddings and, later, tools, and the project-endpoint path when the agent service is added." The rest of 0003 stands, its findings about langchain-azure-ai 1.2.10 included. Supersedes 0004 in part: the entry Settings and model client construction under its Code written here.

## Context

Chat and embedding calls go to the Foundry account's OpenAI v1 route, `<endpoint>/openai/v1`. langchain-azure-ai 1.2.10's `AzureAIOpenAIApiChatModel` and `AzureAIOpenAIApiEmbeddingsModel` subclass langchain-openai's `ChatOpenAI` and `OpenAIEmbeddings`. Given `api_key=`, which is how this repository built them, they hand the value to the parent class and the request is the parent's. Their own `credential=` path builds the OpenAI SDK client itself with the token provider, the base URL and its own headers, and no timeout or retry count, so the values set on the model do not reach the client; the chat subclass also overrides a private method of its parent. The package ships no `py.typed`, so its classes were untyped here and mypy carried an override for them. ADR 0003 took the subclasses for one credential type across chat, embeddings, tools and a project-endpoint path; the credential field this repository uses is `ChatOpenAI`'s own `api_key`, and the design has no managed agent runtime. LangChain's own guidance names langchain-openai for direct Azure OpenAI v1 API access and describes the two packages as complementary, with the Azure classes subclassing the OpenAI ones.

## Decision

- langchain-openai is the direct dependency for the chat and embedding clients, declared as a floor, `langchain-openai>=1.6.7`, with `uv.lock` as the exact pin, 1.6.7. langchain-azure-ai is no longer a dependency.
- `foundry.chat_model` builds `ChatOpenAI` and `foundry.embeddings` builds `OpenAIEmbeddings` at `<endpoint>/openai/v1`. The arguments are passed by field name, `openai_api_base`, `openai_api_key` and `request_timeout`, which carry the aliases `base_url`, `api_key` and `timeout`: the pydantic mypy plugin synthesizes the constructors from field names when `populate_by_name` is set, which both classes set, and `OpenAIEmbeddings` forbids extra arguments, so the aliases do not type-check on it.
- `openai_api_key` is the account key when `FOUNDRY_KEY` is set, otherwise `get_bearer_token_provider(AzureCliCredential(), "https://ai.azure.com/.default")`; both classes hand the key string or the token provider to their SDK clients (the async client gets the provider wrapped to run in an executor), and the SDK calls a provider for each request. `request_timeout` is 60 seconds on both clients; left unset, the classes pass `None` and the SDK client has no timeout. Retries stay at the SDK default of two: the chat model passes `max_retries` only when set, the embeddings model passes its own default of two.
- The chat model sets `use_responses_api` per deployment, true for every deployment except DeepSeek-V4-Pro, which stays on chat completions (ADR 0003), and `stream_usage=True`, which the class leaves unset when a base URL is given.
- The embeddings model keeps `dimensions=1536`, `chunk_size=16` and `check_embedding_ctx_length=False`. The reranker is unchanged.
- The mypy override for `langchain_azure_ai.*` is removed; langchain-openai ships `py.typed`.

## Consequences

- Fifteen packages leave `uv.lock`, 164 to 149: anthropic, azure-ai-contentsafety, azure-ai-contentunderstanding, azure-ai-projects, azure-search-documents, azure-storage-blob, docstring-parser, isodate, langchain, langchain-anthropic, langchain-azure-ai, langgraph, langgraph-prebuilt, langgraph-sdk and six. langgraph is declared directly at step 14; nothing imports it before then.
- The cassettes are unchanged: the embeddings request on the v1 route is the same, and the recorded suite passes without a re-recording.
- Smoke (2026-10-28, `dispute_casework.foundry_smoke` under the Azure CLI identity): all five deployments answered HTTP 200. gpt-5.4-mini and gpt-5.4-nano answered on the Responses API and DeepSeek-V4-Pro on chat completions, each with usage returned; text-embedding-3-large returned 1536 dimensions; Cohere-rerank-v4.0-fast returned a ranking.
- The invariants "model clients carry the explicit timeout under a key and under a token credential" and "`stream_usage` is enabled on the chat model" are backed by `tests/test_foundry.py`; the second no longer waits for step 14.

## Code written here

- 18. Settings and model client construction. Job: read `FOUNDRY_ENDPOINT` and the optional `FOUNDRY_KEY`, strip the endpoint's trailing slash, choose the key or an Entra bearer-token provider per route scope, and pass the clients' arguments: that value as `openai_api_key` (alias `api_key`), the explicit 60-second `request_timeout` (alias `timeout`) on every client, `stream_usage=True` on the chat model, `use_responses_api` for every deployment except DeepSeek-V4-Pro, 16 inputs per request and `check_embedding_ctx_length=False` on embeddings, and `max_retries=7` on rerank; the fields `openai_api_key`, `openai_api_base` and `request_timeout` are named rather than their aliases because the pydantic mypy plugin synthesizes `__init__` from field names when `populate_by_name` is set and `OpenAIEmbeddings` forbids extras. Checked: pydantic-settings 2.15.0, langchain-openai 1.6.7, openai 3.22.1, pydantic 2.13.5, cohere 7.2.0. Why own code: no component reads these two variables, chooses between a key and a token provider, or knows which deployment answers on chat completions; langchain-openai leaves `stream_usage` unset when a base URL is given and leaves the timeout unset unless given, and cohere never waits on the `retry-after-ms` header the rerank route sends. Supersedes in part the entry Settings and model client construction in ADR 0004.

## Rationale

- langchain-openai over langchain-azure-ai for the OpenAI v1 route: it builds the same request through the classes the Azure subclasses extend, with one credential field that takes a key or a token provider and applies the timeout under both, it is the package LangChain names for direct Azure OpenAI v1 API access, and it is typed; industry standard decided, with correctness and reliability agreeing. It replaces the subclasses and their untyped override at the cost of one swapped direct dependency, fifteen packages out of the lockfile and no path to Foundry project endpoints or built-in tools, which the design does not use.

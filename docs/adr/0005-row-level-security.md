# ADR 0005: Row-level security on Azure Database for PostgreSQL

Status: Proposed

## Context

The corpus is read through the vendor's hybrid search, whose two legs run on pooled connections outside the caller's transaction (ADR 0004), so the access tier has to be bound to the connection itself. The design puts one database engine per access tier behind Postgres row-level security, the LangGraph checkpointer in its own schema, and every sign-in on Entra tokens. The spike had to show, on Azure Database for PostgreSQL rather than the compose container, that a role can be bound at connect, that the administrator the service gives us can run the migrations as written, that an Entra user and an Entra group both sign in through the vendor's connection class, that the connection limit holds, and what the managed service refuses.

Claims fixed before the run, each answered under Findings: C1 the subscription can create a flexible server; C2 the libpq startup options `-c role` and `-c search_path` are accepted; C5 a connection outlives its sign-in token; C6/C21 the vendor derives the user name from the token; C10 the SKU is available in the region; C13 the administrator can hand objects to other roles; C14 `CONNECTION LIMIT` applies to an Entra principal; C20 the administrator can create a `BYPASSRLS` role.

Decided before the run and applied as decided: the B1ms server exists for the spike and is stopped between sessions (D8); if C20 fails, the loader owns the table under one `FOR ALL` policy and no role carries `BYPASSRLS`, as one migration set for every environment (F1); the corpus is loaded as the test user with the loader role bound at connect (F3); the test user registers MFA and signs in under its own CLI profile directory (F4); the loader role is granted only for a load (F8); the exit cassette is recorded again after the table change (F9); the administrator SQL is run by hand with psql; East US 2 is left for Central US after six refusals, with South Central US as the fallback (F10 to F13).

## Decision

- **Role bound at connect.** The application signs in as one login holding `dcw_service`, whose memberships in `tier_public`, `tier_full` and `lg_app` carry `INHERIT FALSE`. A connection has no privilege until it binds one of those roles through the libpq option `-c role=<role>`, and it can bind no other; nothing issues `SET ROLE`.
- **One engine per tier.** `database.engine` builds a `PGEngine` from a connection string that names the dialect only and an `async_creator` that carries every connection parameter, the role option among them. `tier_engines` builds one per tier with a pool of 2 and an overflow of 2. The checkpointer runs on a psycopg `AsyncConnectionPool` of 1 to 4 connections opened with `-c role=lg_app -c search_path=lg`. `check_pool_budget` refuses to start when the pools could exceed the login's `CONNECTION LIMIT` of 16.
- **The loader.** `corpus_loader` owns `corpus.chunks`, which is under `FORCE ROW LEVEL SECURITY`, and reads and writes every row through one policy `FOR ALL TO corpus_loader USING (true) WITH CHECK (true)`. No role carries `BYPASSRLS`. The loader holds `USAGE` and `CREATE` on the schema. It is granted to the login immediately before a load and revoked immediately after, by the administrator SQL in `infra/postgres/admin/`; locally the test session does the same around each load.
- **Three migrations, forward only.** Revision 0001 creates the nine `NOLOGIN` roles, grants the four owners and the loader to the runner, grants the tiers and `lg_app` to `dcw_service` with `INHERIT FALSE`, and creates the four schemas with their owners. Revision 0002 lets the vendor create `corpus.chunks` on its own connection in an autocommit block, then enables and forces row-level security, adds one `SELECT` policy per tier and the loader's policy, grants the schema privileges, hands the table to the loader and grants the tiers `SELECT`. Revision 0003 runs the checkpointer's own `setup()` on a connection bound to `lg_owner` with `search_path=lg`, so `lg_owner` owns the four checkpoint tables and its default privileges in `lg` cover them for `lg_app`.
- **Sign-in.** A `DATABASE_URL` without a password selects the vendor's Entra connection classes. The credential is `ChainedTokenCredential(ManagedIdentityCredential(client_id=AZURE_CLIENT_ID), AzureCliCredential())` when `AZURE_CLIENT_ID` is set and `AzureCliCredential` alone otherwise, on the sync and the async path. A user named in the URL is passed to the vendor as a keyword, because the vendor otherwise replaces it with the token's user principal name.
- **Server.** `psql-dcw-cus` in Central US, in the resource group `rg-dcw-eus2`: PostgreSQL 17, `B_Standard_B1ms`, 32 GiB Premium SSD at tier P4, no zone preference, Entra-only authentication, `azure.extensions = vector`, public access with one developer firewall rule. The Entra administrator is the security group `psql-dcw-eus2-administrators`, whose member is the Azure CLI login that runs Terraform and the migrations. The Microsoft.DBforPostgreSQL provider is registered by the bootstrap root.
- **Logins.** The spike's application login is a pre-created Entra user with MFA, signed in under `AZURE_CONFIG_DIR=$HOME/.azure-dcw-test` so that the developer's own CLI login stays separate. It holds `dcw_service` and a `CONNECTION LIMIT` of 16. Its principal, the extension, the grants and the loader grant and revoke are created by the administrator with psql from `infra/postgres/admin/`.
- **Pins.** `langgraph-checkpoint-postgres==3.1.3` is pinned exactly, the second exception to ADR 0001's rule of floors for runtime dependencies, for the reason under Checkpointer in Findings. azurerm is 5.9.0 in the postgres root.

## Findings

Every observation below was made on 2026-10-15 in the run that wrote this record, against PostgreSQL 17.11 with pgvector 0.8.2 on the server above, with psycopg 3.3.6, azure-postgresql-auth 1.1.0, azure-identity 1.25.3 and langgraph-checkpoint-postgres 3.1.3, unless a source file is named.

**C1, provider registration.** The first apply of the postgres root failed on the server with HTTP 409 `MissingSubscriptionRegistration: The subscription is not registered to use namespace 'Microsoft.DBforPostgreSQL'`, after the Entra group and the test user had been created. The registration is declared as `azurerm_resource_provider_registration` in `infra/bootstrap`, as ADR 0002 requires; its apply took three minutes and `az provider show` read `Registered` on the first check.

**C10, SKU availability.** East US 2 refused the server six times, every time after the write had been Accepted, during provisioning, with the same text: `Status: "SkuNotAvailable" Code: "" Message: "Specified SKU is not supported in this region. Please choose a different SKU."`. The attempts: azurerm 5.7.0 with `Standard_B1ms` twice and with `Standard_B2s` once; azurerm 5.9.0 with `Standard_B1ms`; and the portal's own ARM template, saved from a create wizard that had validated `Standard_B1ms` in East US 2, deployed with `az deployment group create` at 32 GiB P4 and at the wizard's 128 GiB P10, whose operation records carry the same code and message with status Conflict. Throughout, `az postgres flexible-server list-skus -l eastus2` listed `Standard_B1ms` and `Standard_B2s` under Burstable in zones 1 to 3 with no restriction, while East US answered "Provisioning is restricted in this region". The portal wizard's validation is a template validation and does not allocate compute, so it cannot see this refusal. A comparison of the azurerm 5.7.0 create payload (`resourcePostgresqlFlexibleServerCreate` and its expand functions) with the template found only encodings of the same values: the provider sends `storage.type = Premium_LRS`, `identity.type = None` and no `createMode`, where the template sends null, null and `Default`. Central US accepted `Standard_B1ms` on the first apply; the server was created in 5 minutes 5 seconds and the Entra administrator assignment in 2 minutes 19 seconds. A refused server lingers in state Dropping for two to three minutes, during which the resource-group listing no longer shows it but the resource still answers on its ID, and a new apply collides on the name; the check before a retry is `az postgres flexible-server show`, not the listing.

**C2, startup options.** Accepted for the administrator and for a plain user. Revision 0003 connected as the administrator with `-c role=lg_owner -c search_path=lg`, and a probe with the same options returned `current_user` lg_owner, `role` lg_owner and `search_path` lg. The test user connected with `-c role=corpus_loader` for the load and with `-c role=tier_public` and `-c role=tier_full` for the smoke; `database_smoke` printed, for each tier, the tier as login and as role and 1,742 chunks visible.

**C5, token lifetime and an idle connection.** The Azure CLI token for the `ossrdbms-aad` resource lived 73 minutes for the developer's login and 93 minutes for the test user, read from the `exp` and `iat` claims. A connection opened as the test user with `-c role=tier_full` and left idle for 100 minutes, 22 minutes past that token's expiry, still answered its first query: `now()`, `current_setting('role')` as `tier_full`, and a count of 1742 rows in `corpus.chunks`. The token is checked at connect only; a session already open is not revoked when it expires.

**C6/C21, user name from the token.** For the test user the token carries `upn`, `unique_name` and `idtyp`, and `upn` and `unique_name` equal the role name the administrator created, byte for byte, so the vendor's derived user name and the URL's user agree. For the group they cannot: the vendor's `EntraConnection.connect` (`azure_postgresql_auth/psycopg3/entra_connection.py` lines 50 to 59, and the async twin at lines 52 to 61) reads `user` from its keyword arguments only and otherwise takes `upn`, `preferred_username` or `unique_name` from the token (`core.py` lines 113 to 120), and psycopg lets keyword arguments override the URL. With the group's name only in the URL, the server answered `FATAL: password authentication failed for user "<the member's user principal name>"` in 2.8 s; with the name as a keyword the same token signed in as `psql-dcw-eus2-administrators` in 0.8 s. `database.named_user` passes the URL's user as a keyword on both paths. A user principal name in a libpq URI needs its at-sign encoded as `%40`; psycopg otherwise reads the domain as the host.

**C13, ownership.** As the administrator, `CREATE SCHEMA ... AUTHORIZATION` produced the four schemas with their owner roles and `ALTER TABLE corpus.chunks OWNER TO corpus_loader` succeeded. Locally the runner, which carries the administrator's attributes, showed the ordering rule first: the ownership transfer before `GRANT CREATE ON SCHEMA corpus TO corpus_loader` failed with `permission denied for schema corpus`, because the new owner of a table must hold `CREATE` on its schema; the grant now precedes the transfer.

**C14, connection limit.** `ALTER ROLE "<user>" CONNECTION LIMIT 16` on the Entra principal answered `ALTER ROLE`. As the test user with `-c role=tier_full`, the first 16 connections opened and the 17th was refused at connect with `FATAL: too many connections for role "<user>"`.

**C20, BYPASSRLS.** Denied. `CREATE ROLE c20_probe NOLOGIN BYPASSRLS` as the administrator answered `ERROR: permission denied to create role` with `DETAIL: Only roles with the BYPASSRLS attribute may create roles with the BYPASSRLS attribute.`; the administrators group does not carry the attribute. The migrations follow the F1 branch in every environment, and the local runner no longer carries `BYPASSRLS` either. Two side effects of the administrator functions: `pgaadauth_create_principal` grants the role it creates to its caller, so the group holds the test user's role; and `CREATE ROLE` leaves the creator a membership with `ADMIN OPTION`, so the group holds every migrated role, the four owners and the loader twice.

**Row-level security on Azure.** `corpus.chunks` reads row security enabled and forced, with the three policies as written in revision 0002. A connection with no role option was refused at the first query with `permission denied for schema corpus`; a role option naming `corpus_loader` after the revoke was refused at connect with `FATAL: permission denied to set role "corpus_loader"`. Both tiers see every row because the current corpus is all `public`; the per-label test runs locally only (`tests/test_rls.py`).

**Checkpointer on Azure.** The four tables exist in `lg` owned by `lg_owner`; one put and get through the `lg_app` pool took 0.9 s; the sentinel placed in `config["configurable"]` was found in `checkpoints.metadata` and nowhere else, and the chunk IDs were in `checkpoint_blobs`, as the local test asserts. `lg.checkpoint_migrations` holds 10 rows, v 0 to 9. The vendor's `setup()` (`langgraph/checkpoint/postgres/__init__.py` lines 93 to 108) reads the highest applied version and executes every later entry of its `MIGRATIONS` list, so a release with more entries changes the schema on the next `setup()`: a floor would let a lockfile update change the database through revision 0003, which has already run. That is why the package is pinned exactly.

**Keyword-leg row order and the cassette.** Adding the `access_label` column changed the tuple width and the physical row order of the table, and the keyword leg orders tied `ts_rank_cd` scores in that order (ADR 0004); one rerank request body of the exit cassette no longer matched. The cassette was recorded again (62 interactions, 2 embedding and 60 rerank, all status 200, bodies hashed) in 2 minutes 57 seconds; the regenerated results file was byte-identical to the committed one and no gate moved.

**Per-row commits during a load.** The vendor's insert loop (`langchain_postgres/v2/async_vectorstore.py`, loop at line 301, commit at line 375) commits every row on its own. The load of 1,742 rows took 309 s against Central US from a developer machine; the whole local suite, which loads the corpus twice per session, runs in about 17 s.

**Credential class.** Inside a `ChainedTokenCredential` the managed-identity link probes the IMDS endpoint with a one-second connection timeout and no retry (`azure/identity/_credentials/imds.py` lines 107 to 112; the chain sets the flag at `chained.py` line 111) and never caches a failed probe (only success sets `_endpoint_available`, lines 113 and 117). On a laptop that cost 1.00 s per token request in three calls, against 6.83 s for the same credential outside a chain. `AzureCliCredential` caches nothing (`azure_cli.py` line 106) and the vendor asks for a token on every connect, so each connection costs one `az` subprocess; a connection opened in 0.7 to 0.8 s. The chain therefore includes the managed-identity link only when `AZURE_CLIENT_ID` is set.

**Revision 0002 imports application code.** The migration builds the table through `retrieval.hybrid_config`, so the stored tsvector column and its language follow the application constant; a later change to that constant changes what the revision creates on a fresh database while leaving an existing one as it was.

**Unmeasured choices.** The pool sizes, 2 plus 2 per tier and 1 to 4 for the checkpointer, were chosen to fit the connection limit and are not measured against any load. The test session loads the corpus twice: once in the store fixture and once more after the row-level security fixture replaces the rows.

**Sign-in mechanics.** `az login` without `--allow-no-subscriptions` completed the test user's MFA registration and then stored nothing, answering "No subscriptions found"; the repeat with the flag stored the tenant-level account.

## Code written here

Each unit is written here because no component does its whole job.

- **Credential selection** (`database.credential`, `database.async_credential`): builds the confirmed chain when a client id is configured and the CLI credential alone otherwise; azure-identity's chain has no conditional link, and its default chain probes IMDS on every call on a laptop (Findings, Credential class).
- **User from the URL** (`database.named_user`): passes a user named in the URL to the vendor as a keyword; the vendor reads the user from keyword arguments only (Findings, C6/C21).
- **Engines, pools and the budget check** (`database.engine`, `tier_engines`, `checkpointer_pool`, `check_pool_budget`): vendor configuration with this project's options, and one arithmetic check that the vendor pools do not do.
- **Migrations** (`migrations/`): own work by the architecture; each revision is SQL or one vendor call with this project's roles and options.
- **Administrator SQL and the smoke** (`infra/postgres/admin/`, `database_smoke.py`): the statements the managed service's administrator functions require, and one connection per tier printing what the server reports.

## Rationale

## Consequences

- A load of this corpus against Azure takes minutes, one commit per row over the network; a larger corpus or a remote developer will want the vendor's bulk path, which is a question for the corpus step, not a reason to write an insert here.
- An Entra group sign-in needs the group's name in `DATABASE_URL`, at-sign encoded where one appears; the test user's name happens to match its token, so a missing name shows only on the group.
- The server is in Central US and the Foundry account in East US 2; the resource group keeps its name. Cross-region latency between the application and the database is not measured here.
- The server is stopped between sessions and Azure restarts it after seven days; the next session starts it with `az postgres flexible-server start`.
- A lockfile update of `langgraph-checkpoint-postgres` is a schema change: it is reviewed as one and applied by a deliberate `setup()` run, never by a pull request alone.
- With `AZURE_CLIENT_ID` set on a machine without a managed identity, every connection pays the one-second probe before the CLI link answers.
- `corpus_loader` reaches the login only through the administrator's grant and revoke around a load; a load that fails leaves the grant in place until the revoke is run.
- The East US 2 refusal is a capacity observation of one day for one subscription; the design's region stays recorded and nothing here forbids returning.

## Open claims not measured

- Token expiry inside a long-lived pool: a pooled connection opened before its token expires keeps working for the C5 interval; what a pool does when it opens a new connection after the CLI login itself has expired is not measured.
- Sign-in through a managed identity: no managed identity exists yet, so the chain's first link has only been observed failing over on a laptop.
- Pool sizes under load, and the latency of a hybrid search from a Container App in East US 2 to the database in Central US.
- Premium SSD v2 storage, which the capability list offers at 32 GiB with 3,000 IOPS, against the P4 tier provisioned.
- Whether East US 2 accepts a Burstable server on another day.

# ADR 0005: Row-level security on Azure Database for PostgreSQL

Status: Accepted. Supersedes 0001, 0002 and 0004 in part: in 0001 the sentence "langchain-postgres is the exception and is pinned exactly; ADR 0004 decides that pin." (there are now two exact pins); in 0002 the sentence "the providers this repository uses (Microsoft.CognitiveServices, Microsoft.Storage, Microsoft.Consumption) were already registered on the subscription, so no registration resource is declared", the providers line "Providers: azurerm 5.7.0 and azapi 2.13.0, pinned exactly, with `.terraform.lock.hcl` committed per root for `linux_amd64` and `darwin_arm64`.", the "Two roots" bullet and the "Naming" bullet (names carry the region of creation and are kept when a resource moves, since a rename is a replacement; Decision, Server); in 0004 the "Table load" entry (superseded in part by the entry Corpus reload).

## Context

The corpus is read through the vendor's hybrid search, whose two legs run on pooled connections outside the caller's transaction (ADR 0004), so the access tier has to be bound to the connection itself. The design puts one database engine per access tier behind Postgres row-level security, the LangGraph checkpointer in its own schema, and every sign-in on Entra tokens. The spike had to show, on Azure Database for PostgreSQL rather than the compose container, that a role can be bound at connect, that the administrator the service gives us can run the migrations as written, that an Entra user and an Entra group both sign in through the vendor's connection class, that the connection limit holds, and what the managed service refuses. The review of the spike kept the strategy and changed the ownership of the corpus table, the reset of a pooled connection and the credential; the Decision below is the form the review settled.

Claims fixed before the spike run, each answered under Findings: C1 the subscription can create a flexible server; C2 the libpq startup options `-c role` and `-c search_path` are accepted; C5 a connection outlives its sign-in token; C6/C21 the vendor derives the user name from the token; C10 the SKU is available in the region; C13 the administrator can hand objects to other roles; C14 `CONNECTION LIMIT` applies to an Entra principal; C20 the administrator can create a `BYPASSRLS` role.

Decided before the spike run and applied as decided: the B1ms server exists for the spike and is stopped between sessions (D8); if C20 fails, no role carries `BYPASSRLS` and the loader writes through one `FOR ALL` policy, as one migration set for every environment (F1); the corpus is loaded as the test user with the loader role bound at connect (F3); the test user registers MFA and signs in under its own CLI profile directory (F4); the loader role is granted only for a load (F8); the exit cassette is recorded again after the table change (F9); the administrator SQL is run by hand with psql; East US 2 is left for Central US after six refusals, with South Central US as the fallback (F10 to F13).

## Decision

- **Who owns the table, who writes, through what.** `corpus_owner` owns the schema `corpus` and the table `corpus.chunks`, which is under `FORCE ROW LEVEL SECURITY`. The only writer is `corpus_loader`: it holds `USAGE` on the schema and `SELECT`, `INSERT`, `UPDATE` and `TRUNCATE` on the table, and every row it reads, inserts or updates passes through the one policy `FOR ALL TO corpus_loader USING (true) WITH CHECK (true)`; `TRUNCATE` is a table privilege that row security does not filter. The writer never owns the table, because the owner of a table can switch row security off (Findings, Ownership), and no role carries `BYPASSRLS`, which the Azure administrator cannot grant (Findings, C20). The tiers hold `USAGE` on the schema and `SELECT` on the table, each behind its own `SELECT` policy. `corpus_loader` is granted to the application login immediately before a load and revoked immediately after, by the administrator SQL in `infra/postgres/admin/`; locally the test session does the same around each load. The grant carries `WITH INHERIT FALSE`, as the `dcw_service` memberships do, so that the login holds no corpus privilege without a role, including while it holds the loader; `SET` stays on, which the `-c role=corpus_loader` binding needs (Findings, The loader grant inherits).
- **Role bound at connect, and its reach.** The application signs in as one login holding `dcw_service`, whose memberships in `tier_public`, `tier_full` and `lg_app` carry `INHERIT FALSE`. A bound session reaches exactly this far: the login can set exactly those three roles and no other; a connection has no privilege on any project schema until the libpq option `-c role=<role>` binds one of them; a `SET ROLE` to another of the three persists for the rest of that checkout; and the pool returns the connection to its bound tier when it takes the connection back. Nothing in the application issues `SET ROLE`.
- **Reset on checkin.** The tier engines run on a pool class that attaches SQLAlchemy's reset event to each pool, with the pool's own reset switched off (`pool_reset_on_return=None`); the hook rolls back, issues `RESET ROLE` and commits, which is SQLAlchemy's documented custom-reset form (Findings, Role reset). The checkpointer pool issues `RESET ROLE` through psycopg_pool's `reset` callback; its connections are opened in autocommit.
- **One engine per tier.** `database.engine` builds a `PGEngine` from a connection string that names the dialect only and an `async_creator` that carries every connection parameter, the role option among them. `tier_engines` builds one per tier with a pool of 2 and an overflow of 2. The checkpointer runs on a psycopg `AsyncConnectionPool` of 1 to 4 connections opened with `-c role=lg_app -c search_path=lg`. `check_pool_budget` runs where the pools are built and refuses to start when the pools of this process could exceed the login's `CONNECTION LIMIT` of 16; the budget across processes belongs to step 4.
- **Three migrations, forward only.** Revision 0001 creates the nine `NOLOGIN` roles, grants the four owners to the runner, grants the tiers and `lg_app` to `dcw_service` with `INHERIT FALSE`, creates the four schemas with their owners, grants `lg_app` `USAGE` on `lg` and sets `lg_owner`'s default privileges in `lg` so that every table it creates there grants `SELECT`, `INSERT`, `UPDATE` and `DELETE` to `lg_app`. Revision 0002 lets the vendor create `corpus.chunks` on its own connection in an autocommit block, naming the tsvector column `content_tsv` itself, then enables and forces row-level security, adds one `SELECT` policy per tier and the loader's policy, hands the table to `corpus_owner`, and grants the schema and table privileges above. Revision 0003 runs the checkpointer's own `setup()` on a connection bound to `lg_owner` with `search_path=lg`, so `lg_owner` owns the four checkpoint tables and its default privileges in `lg` cover them for `lg_app`.
- **Sign-in.** A `DATABASE_URL` without a password selects the vendor's Entra connection classes. The credential is azure-identity's `DefaultAzureCredential(require_envvar=True)`, sync and aio, so that `AZURE_TOKEN_CREDENTIALS` selects the credential: each deployment sets a single credential name, `azureclicredential` for a developer and for the spike's Azure run, `managedidentitycredential` in production from step 4; the vendor also accepts `dev` and `prod`, which build chains and are not used (`azure/identity/_internal/utils.py` lines 209 to 216). The variable is required; without it a connect raises. The credential is opened and closed around each connect. A user named in the URL is passed to the vendor as a keyword, because the vendor otherwise replaces it with the name in the token.
- **Server.** `psql-dcw-cus` in Central US, in the resource group `rg-dcw-eus2`: PostgreSQL 17 (18 is a decision for the corpus step), `B_Standard_B1ms`, 32 GiB Premium SSD at tier P4, no zone preference, Entra-only authentication, `azure.extensions = vector`, public access with one developer firewall rule. The Entra administrator is the security group `psql-dcw-eus2-administrators`, whose member is the Azure CLI login that runs Terraform and the migrations. Both names stay as they are: the server's `name` and the administrator assignment's `principal_name` and `object_id` each force a new resource in azurerm 5.9.0 (`website/docs/r/postgresql_flexible_server.html.markdown` and `postgresql_flexible_server_active_directory_administrator.html.markdown` at tag v5.9.0), so a rename is a replacement, of the server with its data in the first case. The Microsoft.DBforPostgreSQL provider is registered by the bootstrap root.
- **Logins.** The spike's application login is a pre-created Entra user with MFA, signed in under `AZURE_CONFIG_DIR=$HOME/.azure-dcw-test` so that the developer's own CLI login stays separate. It holds `dcw_service` and a `CONNECTION LIMIT` of 16. Its principal, the extension, the grants and the loader grant and revoke are created by the administrator with psql from `infra/postgres/admin/`.
- **Pins and roots.** `langgraph-checkpoint-postgres==3.1.3` is pinned exactly, the second exception to ADR 0001's rule of floors for runtime dependencies, for the reason under Checkpointer in Findings. There are three Terraform roots, `infra/bootstrap`, `infra/foundry` and `infra/postgres`; azurerm is 5.9.0 in all three, azapi stays 2.13.0 in the foundry root and azuread is 3.10.0 in the postgres root, each with its lock file for `linux_amd64` and `darwin_arm64`.

## Findings

The observations below were made on 2026-10-15, in the spike run or in the rebuild run on the same day, against PostgreSQL 17.11 with pgvector 0.8.2 on the server above and PostgreSQL 17.10 with pgvector 0.8.2 on the compose container, with psycopg 3.3.6, psycopg_pool 3.3.3, SQLAlchemy 2.1.1, langchain-postgres 0.0.18, azure-postgresql-auth 1.1.0, azure-identity 1.25.3 and langgraph-checkpoint-postgres 3.1.3, unless a source file or a later date is named. Rebuild-run observations on Azure are under Form A on Azure.

**C1, provider registration.** The first apply of the postgres root failed on the server with HTTP 409 `MissingSubscriptionRegistration: The subscription is not registered to use namespace 'Microsoft.DBforPostgreSQL'`, after the Entra group and the test user had been created. The registration is declared as `azurerm_resource_provider_registration` in `infra/bootstrap`, as ADR 0002 requires; its apply took three minutes and `az provider show` read `Registered` on the first check.

**C10, SKU availability.** East US 2 refused the server six times, every time after the write had been Accepted, during provisioning, with the same text: `Status: "SkuNotAvailable" Code: "" Message: "Specified SKU is not supported in this region. Please choose a different SKU."`. The attempts: azurerm 5.7.0 with `Standard_B1ms` twice and with `Standard_B2s` once; azurerm 5.9.0 with `Standard_B1ms`; and the portal's own ARM template, saved from a create wizard that had validated `Standard_B1ms` in East US 2, deployed with `az deployment group create` at 32 GiB P4 and at the wizard's 128 GiB P10, whose operation records carry the same code and message with status Conflict. Throughout, `az postgres flexible-server list-skus -l eastus2` listed `Standard_B1ms` and `Standard_B2s` under Burstable in zones 1 to 3 with no restriction, while East US answered "Provisioning is restricted in this region". A comparison of the azurerm 5.7.0 create payload (`resourcePostgresqlFlexibleServerCreate` and its expand functions) with the template found only encodings of the same values: the provider sends `storage.type = Premium_LRS`, `identity.type = None` and no `createMode`, where the template sends null, null and `Default`. Central US accepted `Standard_B1ms` on the first apply; the server was created in 5 minutes 5 seconds and the Entra administrator assignment in 2 minutes 19 seconds. A refused server lingers in state Dropping for two to three minutes, during which the resource-group listing no longer shows it but the resource still answers on its ID, and a new apply collides on the name; the check before a retry is `az postgres flexible-server show`, not the listing.

**C2, startup options.** Accepted for the administrator and for a plain user. Revision 0003 connected as the administrator with `-c role=lg_owner -c search_path=lg`, and a probe with the same options returned `current_user` lg_owner, `role` lg_owner and `search_path` lg. The test user connected with `-c role=corpus_loader` for the load and with `-c role=tier_public` and `-c role=tier_full` for the smoke, which showed 1,742 chunks visible for each tier.

**C5, token lifetime and an idle connection.** The Azure CLI token for the `ossrdbms-aad` resource, read from the `exp` and `iat` claims, lived 73 minutes for the developer's login and 93 minutes for the test user in the spike run, and 66.6 and 85.6 minutes for the same two logins in the rebuild run. Microsoft states two lifetimes that do not agree: the Azure Database for PostgreSQL page on Entra authentication says "User tokens are valid for up to 1 hour" (learn.microsoft.com, security-entra-concepts, "What's the token lifetime?") and the Microsoft identity platform page on configurable token lifetimes says "an access token's default lifetime is assigned a random value ranging between 60-90 minutes (75 minutes on average)" (learn.microsoft.com, configurable-token-lifetimes, "Access tokens"); the 93-minute token exceeds both, and the 66.6-minute token exceeds the first. Nothing in the code depends on a lifetime: the token is used once, at connect. A connection opened as the test user with `-c role=tier_full` and left idle for 100 minutes, 22 minutes past that token's expiry, still answered its first query: `now()`, `current_setting('role')` as `tier_full`, and a count of 1742 rows in `corpus.chunks`. The token is checked at connect only; a session already open is not revoked when it expires.

**C6/C21, user name from the token.** For the test user the token carries `upn`, `unique_name` and `idtyp`, and `upn` and `unique_name` equal the role name the administrator created, byte for byte, so the vendor's derived user name and the URL's user agree. For the group they cannot: the vendor's `EntraConnection.connect` (`azure_postgresql_auth/psycopg3/entra_connection.py` lines 45 to 60, and the async twin at lines 45 to 62) reads `user` from its keyword arguments only and otherwise derives it from the token: with an `xms_mirid` claim it parses the claim as a user-assigned identity path and takes its last segment, and it falls back to `upn`, `preferred_username` and `unique_name` only when the claim is absent (`core.py` lines 115 to 119 and 73 to 95); a system-assigned identity's claim parses to nothing, after which the vendor tries the management scope and raises `UsernameExtractionError`. psycopg lets keyword arguments override the URL. With the group's name only in the URL, the server answered `FATAL: password authentication failed for user "<the member's user principal name>"` in 2.8 s; with the name as a keyword the same token signed in as `psql-dcw-eus2-administrators` in 0.8 s. `database.named_user` passes the URL's user as a keyword on both paths. A user principal name in a libpq URI needs its at-sign encoded as `%40`; psycopg otherwise reads the domain as the host.

**Ownership (C13).** As the administrator, `CREATE SCHEMA ... AUTHORIZATION` produced the four schemas with their owner roles and `ALTER TABLE corpus.chunks OWNER TO` succeeded, to `corpus_loader` in the spike and to `corpus_owner` under Form A. The spike's form, in which the loader owned the table, is rejected on a measurement made before the local database was rebuilt: as the application login bound to the owning `corpus_loader`, `ALTER TABLE corpus.chunks NO FORCE ROW LEVEL SECURITY` and `ALTER TABLE corpus.chunks DISABLE ROW LEVEL SECURITY` both succeeded inside one transaction, `pg_class` read `relrowsecurity` and `relforcerowsecurity` false for the table, and the transaction was rolled back. An owner can switch row security off, so the writer never owns the table. Under Form A the same statement as the loader is refused with `must be owner of table chunks` (`tests/test_rls.py::test_corpus_owner_owns_the_chunks_table_and_the_loader_cannot_alter_it`). The new owner of a table must hold `CREATE` on its schema; `corpus_owner` owns the schema and holds it.

**C14, connection limit.** `ALTER ROLE "<user>" CONNECTION LIMIT 16` on the Entra principal answered `ALTER ROLE`. As the test user with `-c role=tier_full`, the first 16 connections opened and the 17th was refused at connect with `FATAL: too many connections for role "<user>"`.

**C20, BYPASSRLS.** Denied. `CREATE ROLE c20_probe NOLOGIN BYPASSRLS` as the administrator answered `ERROR: permission denied to create role` with `DETAIL: Only roles with the BYPASSRLS attribute may create roles with the BYPASSRLS attribute.`; the administrators group does not carry the attribute. The migrations follow the F1 branch in every environment. No role the migrations create, and neither login we create, carries `BYPASSRLS`; locally no role other than a superuser does (`tests/test_rls.py::test_no_role_bypasses_rls`, which checks every non-superuser role and the two logins). Two side effects of the administrator functions: `pgaadauth_create_principal` grants the role it creates to its caller, so the group holds the test user's role; and `CREATE ROLE` leaves the creator a membership with `ADMIN OPTION`, so the group holds every migrated role, and the four owners twice.

**Role reset.** Measured on the compose container as the application login bound to `tier_public`, in psycopg's default transaction mode: after a committed `SET ROLE tier_full`, a `RESET ROLE` followed by a rollback left `current_user` at `tier_full`, and the same `RESET ROLE` followed by a commit returned it to `tier_public`; `DISCARD ALL` returned it too. An uncommitted `SET ROLE` is undone by the rollback at checkin on its own, which is why the tests commit the switch. Through SQLAlchemy pools of one connection with a committed switch on the first checkout, measured on 2026-10-20: the default pool handed the second checkout `tier_full`; the pool class with the reset hook and the pool's own reset off handed it `tier_public` with the backend idle, whether the first checkout closed right after the commit or ran a statement first, and a rollback in the second checkout left it `tier_public`; the hook without its commit handed it `tier_public` with the backend idle in transaction, and a rollback in the second checkout returned `tier_full`; the hook without its rollback committed a driver-level `SET application_name` the caller had left open, which the next checkout read. Under an autocommit isolation level the vendor's `SET LOCAL` for `index_query_options` (`langchain_postgres/v2/async_vectorstore.py` lines 698 to 703) had no effect: `WARNING: SET LOCAL can only be used in transaction blocks`, value unchanged. `DISCARD ALL` also drops prepared statements and temporary tables, `SET ROLE NONE` returns to the session user, which holds no privilege, `RESET ALL` leaves `role` as it is, and invalidating a connection whose `current_user` changed costs a query and a reconnect per checkin; none is used. Through psycopg_pool with the checkpointer's connection options on a pool of one connection, measured on 2026-10-20: `tier_full` without the `reset` callback and `lg_app` with it; with up to four connections the second checkout can be another connection, which is why the test pins the pool to one. SQLAlchemy 2.1.1 refuses a class-level listener on an asyncio pool class with `AttributeError: _set_asyncio`, because `_ClsLevelDispatch` has no such method (`sqlalchemy/event/attr.py` lines 114 and 432, called from `event/registry.py` line 352); the listener is attached per instance in the pool class's constructor. The same readings through the real pools on the server, as the test user on 2026-10-20, are under Form A on Azure.

**Form A on Azure.** The rebuild run dropped the four schemas, `alembic_version` and the nine migrated roles on the server, kept the extension and the test user's principal, and ran the three revisions again as the administrators group in 8.3 s; the first connect as the group took 0.7 s. The server then read: `corpus.chunks` owned by `corpus_owner`, row security enabled and forced, the three policies as written, `corpus_loader` holding `INSERT`, `SELECT`, `TRUNCATE` and `UPDATE` on the table and `USAGE` on the schema, `CREATE` on the schema held by `corpus_owner` alone, the three `dcw_service` memberships with `INHERIT FALSE` and `SET`, the four checkpoint tables owned by `lg_owner`, and `azuresu`, the service's own role, as the only role with `BYPASSRLS`. The load as the test user bound to `corpus_loader` took 199 s. The smoke printed the test user as login and the tier as role, 1,742 chunks visible for each tier. As the loader, `ALTER TABLE corpus.chunks NO FORCE ROW LEVEL SECURITY` was refused with `must be owner of table chunks` and `pg_class` still read both flags true. Through the real pools as the test user, measured again on 2026-10-20 under the transactional reset: the tier engine, bound to `tier_public` with a pool of one, read `tier_public` on the checkout after a committed `SET ROLE tier_full`, whether the first checkout closed right after the commit or ran a statement first, still `tier_public` after a rollback in that checkout, `SET LOCAL work_mem = '64MB'` read back `64MB`, and the backend idle after each checkin, in 2.9 s and 3.0 s for the two checkouts with a CLI token request per connection opened; the checkpointer pool pinned to one connection read `lg_app` on the three checkouts after a `SET ROLE tier_full`, in 1.1 s for the four; the smoke printed the test user as login and 1,742 chunks visible for each tier. After the revoke, a connection with no role option was refused at the first query with `permission denied for schema corpus`, a role option naming `corpus_loader` was refused at connect with `FATAL: permission denied to set role "corpus_loader"`, and the login's only membership was `dcw_service`. No token-expiry hold was run.

**The loader grant inherits.** While `corpus_loader` was granted to the test user, a connection with no role option read all 1,742 rows: `pg_has_role(current_user, 'corpus_loader', 'USAGE')` was true, because `GRANT corpus_loader TO "<user>"` carries `INHERIT TRUE` by default, so for the duration of a load the login holds the loader's privileges and its policy without binding the role. The `dcw_service` memberships carry `INHERIT FALSE` for exactly this reason, and the local fixture's grant had the same default. `grant-loader.sql` and the fixture grant `WITH INHERIT FALSE`, and `tests/test_rls.py::test_the_login_holds_no_corpus_privilege_without_a_role_while_granted_the_loader` holds that during a grant window the login with no role option is refused on the schema and does not inherit the loader, while a connection bound to `corpus_loader` truncates and inserts. On Azure, after `grant-loader.sql` with `WITH INHERIT FALSE` had answered `GRANT ROLE`: the test user's memberships read `corpus_loader` with `inherit_option` false and `set_option` true beside `dcw_service`; with no role option `pg_has_role(current_user, 'corpus_loader', 'USAGE')` was false and the count was refused with `permission denied for schema corpus`; bound to `corpus_loader` the count read 1,742, with no write run; bound to `tier_public` it read 1,742. After `revoke-loader.sql`, the loader option was refused at connect with `permission denied to set role "corpus_loader"`.

**Checkpointer on Azure.** The four tables exist in `lg` owned by `lg_owner`; one put and get through the `lg_app` pool took 0.9 s; the sentinel placed in `config["configurable"]` was found in `checkpoints.metadata` and nowhere else, and the chunk IDs were in `checkpoint_blobs`, as the local test asserts. `lg.checkpoint_migrations` holds 10 rows, v 0 to 9. The vendor's `setup()` (`langgraph/checkpoint/postgres/__init__.py` lines 93 to 108) reads the highest applied version and executes every later entry of its `MIGRATIONS` list. The package is pinned exactly because an upgrade leaves installed code expecting a schema that a new revision must supply: revision 0003 has already run, so a lockfile update alone would leave the database behind the code until a deliberate `setup()` run.

**Keyword-leg row order and the cassette.** Adding the `access_label` column changed the tuple width and the physical row order of the table, and the keyword leg orders tied `ts_rank_cd` scores in that order (ADR 0004); one rerank request body of the exit cassette no longer matched. The cassette was recorded again (62 interactions, 2 embedding and 60 rerank, all status 200, bodies hashed) in 2 minutes 57 seconds; the regenerated results file was byte-identical to the committed one and no gate moved.

**Per-row commits during a load.** The vendor's insert loop (`langchain_postgres/v2/async_vectorstore.py`, loop at line 301, commit at line 375) commits every row on its own. The load of 1,742 rows took 309 s against Central US from a developer machine in the spike run and 199 s in the rebuild run; the same load against the compose container took 3.3 s. The load is not atomic: a load that fails midway leaves the table partly filled, a limitation carried to the corpus step together with F9.

**Credential selection.** Inside a chain, azure-identity's managed-identity link probes the IMDS endpoint with a one-second connection timeout and no retry (`azure/identity/_credentials/imds.py` lines 107 to 112; the chain sets the flag at `chained.py` line 111) and never caches a failed probe (only success sets `_endpoint_available`, lines 113 and 117). On a laptop that cost 1.00 s per token request in three calls, against 6.83 s for the same credential outside a chain. `DefaultAzureCredential` with `AZURE_TOKEN_CREDENTIALS=managedidentitycredential` builds the managed-identity link alone and with the probe off (`_credentials/default.py` line 279 and `aio/_credentials/default.py` line 242, `_enable_imds_probe=token_credentials_env != "managedidentitycredential"`); with `azureclicredential` it builds the CLI link alone (`_internal/utils.py` lines 209 to 232), which caches nothing (`azure_cli.py` line 106), so each connect costs one `az` subprocess; a connection opened in 0.7 to 0.8 s. The variable is required so that no environment falls back to the full chain (`tests/test_database.py::test_sign_in_refuses_to_guess_a_credential`).

**Revision 0002 names the tsvector column.** The vendor reads only `tsv_column` when it creates the table (`langchain_postgres/v2/engine.py` lines 236 to 244) and applies `tsv_lang` at insert and search time (`async_vectorstore.py` lines 327, 722 and 1008). The revision names `content_tsv` itself and imports nothing from the application; `retrieval.hybrid_config` names the same column (`tests/test_retrieve.py::test_hybrid_config_names_the_stored_column_and_rrf`), and a search on a mismatched name fails against the table.

**Unmeasured choices.** The pool sizes, 2 plus 2 per tier and 1 to 4 for the checkpointer, were chosen to fit the connection limit and are not measured against any load. The test session loads the corpus twice: once in the store fixture and once more after the row-level security fixture replaces the rows.

**Sign-in mechanics.** `az login` without `--allow-no-subscriptions` completed the test user's MFA registration and then stored nothing, answering "No subscriptions found"; the repeat with the flag stored the tenant-level account.

## Code written here

Each unit is written here because no component does its whole job. The components named were checked at the versions in the Findings preamble by reading their source in the run that wrote the entry.

- **User from the URL** (`database.named_user`): passes a user named in the URL to the vendor as a keyword. `EntraConnection.connect` and its async twin read the user from keyword arguments only (`azure_postgresql_auth/psycopg3/entra_connection.py` lines 45 to 60; `async_entra_connection.py` lines 45 to 62). The vendor's SQLAlchemy hook `enable_entra_authentication_async` was the other candidate; it fetches the token synchronously inside the event loop, as its docstring states (`azure_postgresql_auth/sqlalchemy/async_entra_connection.py` lines 34 to 35), which would block the engines' loop on every connect.
- **Sign-in path selection** (`DatabaseSettings.entra`, `database.connect`, `database.async_connection`, `database.AsyncTokenConnection`): selects the vendor's Entra connection classes when the URL carries no password and the plain psycopg classes otherwise, and opens the vendor's default credential for exactly one connect. The credential itself is the vendor's, `DefaultAzureCredential(require_envvar=True)`, with the credential chosen by `AZURE_TOKEN_CREDENTIALS` (`azure/identity/_internal/utils.py` lines 209 to 232; `_credentials/default.py` lines 175 to 177; `aio/_credentials/default.py` lines 149 to 153). An async credential is to be closed (azure-identity METADATA line 91) and its transport opens an aiohttp session on the loop of its first request (`azure/core/pipeline/transport/_aiohttp.py` line 196). psycopg_pool 3.3.3 accepts `kwargs` as a dict or a callable resolved at each connect (`psycopg_pool/pool_async.py` lines 695 and 731 to 739), so the checkpointer pool could hold one credential for its life on the application's loop; the tier engines connect on a loop the vendor keeps private (`langchain_postgres/v2/engine.py` lines 104 to 110), where closing a long-lived credential would need the vendor's private `_run_as_async` (line 115), so one connection class opens and closes the credential around each connect on both paths.
- **Role reset on checkin** (`database.RoleBoundPool`, `database.reset_role_on_return`, `database.reset_role`): rolls back, issues `RESET ROLE` and commits when a pool takes a connection back. SQLAlchemy 2.1.1's `reset_on_return` offers rollback, commit or none (`sqlalchemy/pool/base.py` lines 283 to 290) and the `PoolEvents.reset` hook for anything else (`sqlalchemy/pool/events.py` lines 206 to 219), which its documentation pairs with `pool_reset_on_return=None` and a hook that also rolls back (`sqlalchemy/dialects/mssql/base.py` lines 527 to 553). The hook attaches to a pool class, a pool or an `Engine` (`pool/events.py` lines 66 to 87); the engine behind a `PGEngine` is the private `_pool` (`langchain_postgres/v2/engine.py` line 73), and `PGEngine.from_engine` builds no loop thread, after which the sync vector-store calls raise (`engine.py` lines 78 to 84 and 125 to 128), so the listener belongs to a pool subclass passed as `poolclass`; SQLAlchemy 2.1.1 refuses a class-level listener on an asyncio pool class (Findings, Role reset), so the subclass attaches it to each instance in its constructor. `create_engine`'s `pool_events` keyword attaches a listener per instance without a subclass and is marked deprecated in the source (`sqlalchemy/engine/create.py` line 872), so it fails the upgrade bar. The hook's rollback discards what a caller left open at the driver level, which the pool's own reset no longer does, and its commit makes the `RESET ROLE` outlive the next rollback (Findings, Role reset). psycopg_pool 3.3.3 runs its `reset` callback on every checkin (`psycopg_pool/pool_async.py` lines 60 and 900 to 911) and the checkpointer pool opens its connections in autocommit; the callback is one `RESET ROLE`.
- **Engines, pools and the budget check** (`database.engine`, `tier_engines`, `checkpointer_pool`, `check_pool_budget`): vendor configuration with this project's options, and one arithmetic check that the vendor pools do not do, run where the pools are built.
- **Corpus reload** (`corpus.load`; supersedes in part ADR 0004's "Table load"): truncates `corpus.chunks` on a connection bound to `corpus_loader`, inserts the snapshot's rows through the vendor's store on an engine bound to the same role with `access_label` `public` on every row of this step, and closes the engine whether or not the insert completes; row IDs stay `uuid5(snapshot:paragraph_id)`. The vendor's `init_vectorstore_table(overwrite_existing=True)` drops and recreates the table (`langchain_postgres/v2/engine.py` lines 218 to 223), which the loader may not do and which would discard the policies; `adelete` needs ids or a filter (`async_vectorstore.py` lines 424 to 441) and the `DELETE` privilege the loader does not hold; no vendor call truncates.
- **Migrations** (`migrations/`): own work by the architecture; each revision is SQL or one vendor call with this project's roles and options.
- **Administrator SQL and the smoke** (`infra/postgres/admin/`, `database_smoke.py`): the statements the managed service's administrator functions require, and one connection per tier printing what the server reports.
- **Vendor configuration and test code**: `DatabaseSettings`, the pool sizes and connection options, `migrations/env.py`, `compose.yaml`, `pyproject.toml`, `.github/dependabot.yml`, `src/dispute_casework/py.typed`, the Terraform roots and the tests under `tests/`, listed as one class.

## Rationale

- **What it does.** The corpus is read through one database engine per access tier. Every connection of a tier engine binds its role at connect through the libpq startup option `-c role=<role>` and is returned to that role when the pool takes it back, by a reset hook that rolls back, issues `RESET ROLE` and commits with the pool's own reset off; the checkpointer's four tables in `lg` are owned by `lg_owner`, and `lg_app`, which reads and writes them through `lg_owner`'s default privileges, runs on its own pool bound with `search_path=lg`, whose reset callback issues `RESET ROLE` on autocommit connections. `corpus.chunks` is owned by `corpus_owner` under `FORCE ROW LEVEL SECURITY`, with one `SELECT` policy per tier and one `FOR ALL` policy for `corpus_loader`, the only writer, which holds `SELECT`, `INSERT`, `UPDATE` and `TRUNCATE` on the table and never owns it. The application signs in as one login holding `dcw_service`, whose memberships carry `INHERIT FALSE`, so a connection has no privilege on any project schema until the option binds one of the three roles; a bound session can set another of the three for the rest of its checkout, and the pool returns it to its tier at checkin; a `DATABASE_URL` without a password signs in through the vendor's Entra connection classes with the one credential `AZURE_TOKEN_CREDENTIALS` names, opened and closed around each connect. Nothing in the application issues `SET ROLE`.
- **What it changed and cost.** Against the spike's first form, the step moved the ownership of `corpus.chunks` from the loader to `corpus_owner`, because an owner can switch row security off; replaced the pool's own reset on the tier engines with the hook that rolls back, resets the role and commits, so that a committed `SET ROLE` does not reach the next checkout and the reset outlives a rollback in it, while what a caller left open at the driver level is rolled back first; put `INHERIT FALSE` on the loader grant, as the `dcw_service` memberships already carry it, so that the login holds no corpus privilege without a bound role, including during a load; passed a user named in the URL to the vendor as a keyword, so that an Entra group signs in under its own name; replaced the credential chain with the one credential `AZURE_TOKEN_CREDENTIALS` names; and made the pool builders run `check_pool_budget`, which refuses to start a process whose pools could exceed the login's `CONNECTION LIMIT` of 16. Against ADR 0004's table load, the table is created once by migration revision 0002, in the `corpus` schema and with the `access_label` column, and `load` truncates it as `corpus_loader` and inserts through the vendor's store instead of creating it. It cost one token request per connection opened; a loader window the administrator opens and closes around each load, which a session bound to the loader keeps until it closes; a load that commits one row at a time over the network and is not atomic; a second exact pin, `langgraph-checkpoint-postgres`, whose lockfile update is a schema change; one re-recording of the exit cassette after the table change; and a B1ms server in Central US, stopped between sessions, with the cross-region latency to the Foundry account not measured.
- **Why this over the alternative.** The role is a property of the connection rather than a transaction-scoped setting, because the vendor's hybrid search runs its two legs on two pooled connections of its own, outside anything the caller began (correctness), and it is bound at connect rather than by a `SET ROLE` on checkout, so that the tier is the session's own default role: the application issues no statement to set it, and `RESET ROLE` or `DISCARD ALL` returns the connection to it rather than to the login, which holds no privilege (correctness). `corpus_owner` owns the table and the loader writes through one `FOR ALL` policy rather than owning the table or carrying `BYPASSRLS`, because an owner can switch row security off and the Azure administrator cannot create a `BYPASSRLS` role, so one migration set serves every environment (correctness, then reliability). The reset is `RESET ROLE` in SQLAlchemy's documented custom-reset form, the `reset` event with `pool_reset_on_return=None` and a hook that also rolls back, rather than the pool's own rollback, commit or none, `SET ROLE NONE`, `RESET ALL`, `DISCARD ALL`, invalidating the connection or the `pool_events` keyword: the pool's own forms issue no reset of the role and its default rollback handed the second checkout the switched role, `SET ROLE NONE` returns to the session user, which holds no privilege, and `RESET ALL` leaves `role` as it is (correctness); `pool_events` is marked deprecated in the vendor's source (reliability); `DISCARD ALL` and invalidation return the role too, and with correctness and the documented form equal the narrower effect breaks the tie, since `DISCARD ALL` also drops prepared statements and temporary tables and invalidation costs a query and a reconnect per checkin. The listener is attached per pool instance because SQLAlchemy 2.1.1 refuses a class-level listener on an asyncio pool class (correctness). Sign-in uses the vendor's connection classes with one credential named by the environment rather than the vendor's SQLAlchemy hook, a credential chain or a long-lived credential per pool: the hook fetches the token synchronously inside the event loop, which would block the engines' loop on every connect (reliability); inside a chain the managed-identity link probes the IMDS endpoint on every token request with a one-second timeout, no retry and no caching of a failed probe (reliability); and the tier engines connect on a loop the vendor keeps private, where closing a long-lived credential would need the vendor's private `_run_as_async` (reliability). The URL's user is passed as a keyword rather than derived from the token because no claim of a member's token carries an Entra group's name (correctness). The reload truncates as the loader and inserts rather than using the vendor's `init_vectorstore_table(overwrite_existing=True)` or `adelete`, because the first drops and recreates the table, which the loader may not do and which would discard the policies, and the second needs ids or a filter and a `DELETE` privilege the loader does not hold (correctness). `langgraph-checkpoint-postgres` is pinned exactly rather than floored because its `setup()` applies every later entry of its migration list, so an upgrade would leave the database behind the installed code until a deliberate `setup()` run (reliability).

## Consequences

- A load of this corpus against Azure takes minutes, one commit per row over the network, and is not atomic; both are questions for the corpus step, not a reason to write an insert here.
- An Entra group sign-in needs the group's name in `DATABASE_URL`, at-sign encoded where one appears; the test user's name happens to match its token, so a missing name shows only on the group.
- `AZURE_TOKEN_CREDENTIALS` is a required variable in every environment that signs in with a token; a process without it fails at the first connect rather than probing credentials.
- A credential is built and closed for every connect. With the managed identity that is one token request per connection opened, which the pools open rarely; with the CLI it is the one `az` subprocess the credential would run anyway.
- The server is in Central US and the Foundry account in East US 2; the resource group keeps its name. Cross-region latency between the application and the database is not measured here.
- The server is stopped between sessions and Azure restarts it after seven days; the next session starts it with `az postgres flexible-server start`.
- A lockfile update of `langgraph-checkpoint-postgres` is a schema change: it is reviewed as one and applied by a deliberate `setup()` run, never by a pull request alone.
- `corpus_loader` reaches the login only through the administrator's grant and revoke around a load. The revoke stops new bindings; a session bound to `corpus_loader` during the window keeps the loader's reach until it closes, so `revoke-loader.sql` runs after the loading process has exited. A load that fails leaves the grant in place until the revoke is run.
- A system-assigned managed identity signs in only with its name in `DATABASE_URL`; the vendor derives a user-assigned identity's name from its token (`core.py` lines 73 to 95 and 115 to 119).
- The East US 2 refusal is a capacity observation of one day for one subscription; the design's region stays recorded and nothing here forbids returning.

## Open claims not measured

- Token expiry inside a long-lived pool, per pool. The checkpointer pool closes a connection after psycopg_pool's default `max_lifetime` of 60 minutes and gives up on reconnecting after its default `reconnect_timeout` of 300 s (`psycopg_pool/pool_async.py` lines 65 and 67); what happens when it opens a new connection after the credential can no longer produce a token is not measured. The tier engines never recycle a connection (SQLAlchemy's `pool_recycle` default of -1, `sqlalchemy/pool/base.py` line 170), so a tier connection lives until it breaks and a new one is opened only then. On the production path the credential is the managed identity, which has no login to expire; on the developer path it is the CLI login, which does.
- Sign-in through a managed identity: no managed identity exists yet, so the managed-identity link has only been observed failing over on a laptop, inside the chain the spike used.
- Pool sizes under load, and the latency of a hybrid search from a Container App in East US 2 to the database in Central US.
- Premium SSD v2 storage, which the capability list offers at 32 GiB with 3,000 IOPS, against the P4 tier provisioned.
- Whether East US 2 accepts a Burstable server on another day.

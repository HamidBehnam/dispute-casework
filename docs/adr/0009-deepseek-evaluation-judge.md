# ADR 0009: DeepSeek-V4-Pro as the evaluation judge

Status: Accepted.

## Context

The scheduled evaluation run scores the agent's answers with model-judged DeepEval metrics, Faithfulness and GEval, and needs a judge from a model family other than the agent's, sold directly by Azure on the existing Foundry account. The candidates were DeepSeek-V4-Pro, then Mistral-Large-3, then Llama; a candidate is kept when its answers parse into the metrics' schemas, and the next one is tried when it fails. Every judge answer must arrive as the schema the metric asks for, so the judge is chosen by schema validity over 100 real measurements. The figures are in `docs/results/0009-judge-selection.json`, generated by `evals/judge_results.py` from the raw readings under `docs/results/0009-judge-selection-raw/`; this record names their keys.

## Decision

- **The judge is DeepSeek-V4-Pro** on the account's OpenAI v1 route, on chat completions (`use_responses_api` is off for it), through the same `foundry.chat_model` as the agent's models, so it takes the account key or an Entra token provider.
- **A DeepEval custom model.** `evals/judge_model.py` subclasses DeepEval's `DeepEvalBaseLLM`, the interface DeepEval requires for a model it does not ship. With a schema, a request asks for JSON mode (`response_format={"type": "json_object"}`) at temperature 0. The answer is parsed by `trimAndLoadJson`, the helper DeepEval's metrics use for a text answer, and validated with the schema's `model_validate`. Text that is not JSON raises `ValueError`; JSON that does not fit the schema raises pydantic's `ValidationError`.
- **Timeout and retries.** The client's timeout is 360 seconds, at least twice the longest single attempt in the raw readings (178.7 seconds), and its SDK retry count is 8. Both were set after the selection runs and were not measured by them: `method.measured_with` records that the runs used 1740 seconds with the SDK's default of 2 retries, and 1740 seconds with 5 retries for the re-run.
- **The gate is a count over 100 measurements** (25 cases, 2 repeats, Faithfulness and GEval). With s judge failures and t transport failures, the judge fails when s ≥ 2, passes when s < 2 and t = 0, and is otherwise undecided by transport. A measurement stopped by the environment is not counted (`method.gate`).
- **The judge passes.** The first counted run was undecided by transport: 92/100 valid (92%), no judge failure and 8 transport failures (`runs.first-run.measurements`). An uncounted diagnostic followed (`runs.diagnostic`, `counted: false`). The counted re-run passed: 100/100 valid (100%), with no judge or transport failure (`runs.rerun.measurements`). Its Wilson 95% interval runs from 0.963 to 1: no failure was measured, which does not show a true validity of at least 99%.
- **The results file is generated, not written by hand.** `evals/judge_results.py` reads the committed raw readings, computes the counts, the Wilson intervals with scipy and the cost estimates, and writes the file. A test regenerates it and fails when the committed file differs. The response headers of failed attempts are not committed with the raw request rows.
- **DeepEval stays out of the application.** `evals/` sits outside the package, DeepEval is in the development group, and the image installs no development group.

## What it does

The scheduled run's metrics call DeepSeek-V4-Pro through the project's own chat client and receive their schema's instance or an exception; a valid answer is never altered. The same client applies the account's credentials, the timeout and the retries as it does for the agent's models. The judge-selection figures can be regenerated from the committed readings at any time.

## What it changed and what it costs

The repository gains an `evals/` folder with the judge and the results generator, `chat_model` takes a timeout and a retry count, and the development group declares `openai` and the three packages the tests import directly. From the re-run's tokens and the retail prices committed beside the readings, the judge costs 2.011376 USD per scheduled run of 450 measurements per metric with the prompt cache's discount and 2.930096 USD without it, and the six-arm comparison of 2,700 measurements per metric costs 7.57731 USD for Faithfulness and 4.490943 USD for GEval with the discount and 11.810772 and 5.769802 USD without it (`runs.rerun.cost.estimate_usd` and `estimate_usd_without_cache`). Every attempt that received no answer was a TLS handshake on a new connection that the far end closed: 47/318 (15%) in the diagnostic and 61/402 (15%) in the re-run (`runs.*.transport.handshake_failures_of_new_connections`), while no attempt on a reused connection failed at the transport (the raw request rows). Which device on the path closes them is not established. In the re-run the SDK's retries recovered every one of them: none of its 100 measurements ended in a transport failure. The shipped timeout and retry count rest on the readings, not on a measurement of their own. The cost estimates assume the golden set's prompts are the size of the selection inputs.

## Why it over the alternatives

Microsoft's catalog of Foundry Models sold directly by Azure lists DeepSeek-V4-Pro with JSON among its response formats, and its retirement schedule gives version 2026-04-23 general availability with retirement on 2028-02-22. Mistral-Large-3 also answers in JSON but is a preview model in both listings, with no retirement date. Llama-3.3-70B-Instruct and Llama-4-Maverick-17B-128E-Instruct-FP8 answer in text only, without tool calling, and retire on 2027-02-03. DeepSeek-V4-Pro passed the gate, so Mistral-Large-3 and the Llamas were not measured; their comparison rests on the catalog. DeepEval's own model classes do not fit the route and the credential: `OpenAIModel` and `LocalModel` take the API key as a string and wrap it as a secret, so the project's Entra token provider is outside their contract; `AzureOpenAIModel` requires an `api_version` and calls the deployments route, not the v1 route; `DeepSeekModel` calls DeepSeek's own API. DeepEval's model-side parse helper, `trim_and_load_json`, removes a comma before a closing bracket or brace before it parses, which alters a valid answer whose text contains ", }" or ", ]"; `trimAndLoadJson` parses first and strips a trailing comma only after a failed parse.

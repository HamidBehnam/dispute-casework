# ADR 0008: Workforce identity in a separate Entra tenant

Status: Accepted.

## Context

The users are the bank's own staff in three roles: preparer, approver and restricted viewer. Every request to the backend must carry a token that names the user and the roles, and the MCP server must receive a token of its own audience for the same user. The demonstration accounts sign in unattended, so they cannot carry multifactor authentication, and they must not weaken the sign-in of the administrators who run the subscription. The root `infra/identity` provisions the registrations, and `infra/identity/personas.py` provisions the accounts.

## Decision

- **A workforce tenant of its own.** The application registrations and the demonstration accounts live in an Entra workforce tenant apart from the tenant of the Azure subscription. The `azuread` provider names that tenant explicitly through `identity_tenant_id`, so it never falls back to the subscription's tenant. Security defaults are turned off in that tenant only, once, in the Entra admin center: a one-time tenant setting made in the portal rather than in code.
- **Three registrations, single-tenant.** The API and the MCP server each expose one delegated scope, `access_as_user`, and the same three app roles, and both issue version 2 tokens. The web registration is a single-page application whose redirect URIs are the `/redirect` page on the application's own origin and, for local runs, on localhost. Admin consent is granted for every delegated permission, so no account sees a consent prompt, and the API's service principal holds consent for the MCP scope, which On-Behalf-Of needs.
- **App-role assignment required** on the API and MCP service principals, so Entra refuses a token to a member assigned none of their roles. Microsoft does not apply the requirement to a Global Administrator, and no administrator is a user of the application.
- **Browser sign-in with MSAL** (`@azure/msal-browser` 5.29.1), by popup or redirect, through MSAL's redirect bridge page. The backend serves the bridge from the application's origin with `Cache-Control: no-store` and no `Cross-Origin-Opener-Policy` header. The page shows the principal only when `/me` answers 2xx; otherwise it shows `/me`'s status, or the error code, sub-code and number of an MSAL error. The build refuses to run when the tenant or either client ID value is missing or empty.
- **Token verification in the API** is one PyJWT call: RS256 against the tenant's key set, the exact v2 issuer, the API's client ID as audience, `exp`, `nbf`, `iat`, `iss` and `aud` required, and 300 seconds of clock skew, Microsoft.IdentityModel's default. The token must also carry `access_as_user` among its `scp` values, and the principal it yields is the object ID and a set drawn from the three roles. A missing or invalid token answers 401 with `WWW-Authenticate: Bearer`, and a key set that cannot be fetched, or is not JSON, answers 503. `/me` and `/stream` require the token; the sign-in pages do not.
- **The MCP verifier** is FastMCP's `JWTVerifier` configured with the issuer, key set, audience, RS256 and the `access_as_user` scope set explicitly.
- **On-Behalf-Of with a certificate.** `mcp_token` exchanges a caller's API token for a token of the MCP audience through azure-identity's `OnBehalfOfCredential`, one credential per incoming token, closed after its one request, and returns only the MCP token; the tests and the local sign-in suite call it, and its first call site in the backend comes with the MCP server. The credential signs its client assertion with the API registration's certificate, a self-signed RSA certificate generated in Key Vault with an exportable key and a validity of 12 months; the API registration holds that certificate and no client secret.
- **Demonstration accounts** are two per role and one member with no role. `personas.py` plans and applies them: it stores each generated password in Key Vault before the user exists, creates only missing users and assignments, reads which passwords are stored without reading their values, and stops on an incomplete answer from Microsoft Graph. A second apply changes nothing.
- When the application is first deployed, the passwords move to a Key Vault on which the application's identities hold no role, and the localhost redirect URI moves to a separate development registration.

## What it does

A member of the identity tenant signs in on the application's own page, and MSAL obtains an access token for the API. The backend verifies the token on every route but the sign-in pages and reads the roles from it. On-Behalf-Of turns that token into one of the MCP audience for the same user, so the MCP server is never handed the user's API token. Apart from a Global Administrator, only a member assigned a role receives either token.

## What it changed and what it costs

Identity is a second Entra tenant. Creating it required a paid licence in the subscription's tenant, since only paid customers can create a new workforce tenant; the new tenant is billed as a Microsoft Entra ID Free asset. Security defaults are off in the identity tenant, which removes their protection there: the demonstration accounts sign in with a password only. Security defaults are a setting of each directory, so the subscription's tenant keeps its own. That setting is made in the admin center, not through the msgraph Terraform provider, and nothing reads it back; Microsoft may turn security defaults back on in a tenant that has no Conditional Access policy, no premium licence and no legacy-authentication client in use, which would put a multifactor prompt in front of the demonstration accounts. The On-Behalf-Of certificate has no automatic renewal: Entra trusts a renewed certificate only after this root uploads it, so renewal is an apply before the date in the `obo_certificate_expires` output, and its key is exportable because the backend signs the assertion in process. The bearer check accepts a principal with no roles; refusing such a principal is the policy engine's job. The API accepts a token up to 300 seconds past its expiry, and FastMCP's verifier accepts a token without `exp` or `nbf` and never reads `iat`; Entra sets all three, and the verifier parity tests record both verifiers' verdicts. Every build needs the three identity values, and CI builds with placeholders.

## Why it over the alternatives

Entra External ID configures a tenant for consumer and business-customer apps; the users here are staff, which is the workforce configuration. One tenant with Conditional Access exempting the demonstration accounts would keep those accounts in the subscription's tenant and needs a P1 licence for its users; security defaults require all users to register for multifactor authentication, so they cannot leave the demonstration accounts out, and turning them off there removes their protection for the administrators as well. A managed identity as a federated credential would avoid the certificate, but the app registration must belong to the same tenant as the managed identity, and the API registration lives in the identity tenant while the managed identities live in the subscription's. FastMCP's `AzureJWTVerifier` also accepts the `api://` form of the client ID as audience, while a v2.0 token's audience is always the client ID of the API, so the explicit `JWTVerifier` admits exactly what Entra issues. Key Vault roles on individual secrets would narrow what the application's identities can read, but Microsoft recommends a vault per application with roles at vault scope.
